8. Loading weights and proving parity

A model that loads and produces fluent text can still be wrong. Prove yours matches the reference, learn what agreement in bfloat16 actually looks like, and how to find the first layer that disagrees.

By the end of this lesson you can

  • Set up a pinned Python reference to compare against
  • Decide what counts as a match when both sides compute in bfloat16
  • Bisect a mismatch down to the first layer and operation that differs
  • Recognize a greedy-decoding near-tie and tell it apart from a bug

Why text is not enough

Get the RoPE base wrong, swap two projections, or forget QK-norm, and a 0.6B model often still writes grammatical English. It is just a slightly worse model, and you might not notice for weeks. The only reliable check is numerical: run the same input through your implementation and through a trusted one, and compare the logits, the raw scores for every vocabulary entry at every position.

The trusted implementation here is Python's mlx-lm, which runs on the same MLX core. Pin it to the same core version as the Swift package. mlx-swift 0.32.3 bundles MLX 0.32.2, so:

uv venv ref && VIRTUAL_ENV=ref uv pip install "mlx==0.32.2" "mlx-metal==0.32.2" mlx-lm
ref/bin/python - <<'PY'
import mlx.core as mx
from mlx_lm import load
model, _ = load("mlx-community/Qwen3-0.6B-4bit")
ids = mx.array([[9707, 11, 1246, 525, 498, 30, 358, 1079]])   # same ids as infer's logits mode
mx.save_safetensors("python.safetensors", {"logits": model(ids).astype(mx.float32)})

Then load both files in Python and compare position by position.

What a match looks like

The very first comparison made for this course, Qwen3-0.6B at 4 bits on the four tokens of <|im_start|>user Hello, gave:

position          0      1       2       3
max |Δ logit|     0      0.69    0.34    0.39      (logits reach about 16)
argmax agrees     yes    yes     yes     yes

Is that a pass? Position 0 is exact, every position picks the same top token, and the differences are a few bfloat16 steps. A logit near 16 has a bfloat16 step of 0.125, so 0.69 is about five steps. That is the signature of the same computation with operations rounded in a slightly different order somewhere, not of a wrong computation. A real bug looks very different: large differences from the first position on, or a different top token at most positions.

But "looks like rounding" is a hypothesis, and position 0 being exact is a useful clue: at position 0 a token attends only to itself, so whatever differs must involve mixing information across positions. That narrows the search to attention.

Bisecting a difference

The method is simple: dump the hidden state after every layer from both implementations, and find the first layer where they differ. A temporary debug function in Swift saved each layer's output; the Python side looped over model.model.layers the same way. The result:

layer   max |Δ|    max |h|
0       0          7.4
1       0          12.6
2       0          7968       ← the residual stream gets large here
3       0          7968
4       0.0078     7968       ← first difference: one bf16 step, inside attention
5       0.031      7968
...
27      3.9        5120

Layers 0 to 3 are bit-identical. The first difference is one bfloat16 step in layer 4's attention output at a single position, and from there it spreads and grows, because each layer adds to the residual stream and a value of 8,000 has a bfloat16 step of 32. By layer 27 the absolute difference is 3.9, which is still smaller than one step at that magnitude.

Zooming in further, each of the fast kernels involved (RoPE and fused attention) was run alone on the same inputs in Swift and Python, and matched bit for bit. Fusing silu(gate) * up to match Python's compiled swiglu changed nothing. So the remaining difference is below the level of our code: the same Metal source, compiled by a different Metal compiler for the Swift build than for the Python wheel, can round one value differently on particular inputs. You can stop here. The implementation is correct, and you now know the tolerance to expect.

The general lesson. Treat "matches to the last digit" as unattainable across builds, and "same top token everywhere, differences of a few steps at the logit's magnitude, exact where no cross-position mixing happens" as the pass condition. Then test it on more than one prompt.

Greedy near-ties

The other comparison is end-to-end: generate 200 tokens greedily (always the top token) in both implementations. With the prompt "Why is the sky blue?", the first 35 tokens are identical, then they part ways. Is that a bug?

Check the logits at the divergence point:

top candidates at token 35:   " all" 21.875    " a" 21.75    " various" 21.75
Python chose " all"; Swift chose " a"

The top two are 0.125 apart, exactly one bfloat16 step at that magnitude. A one-step difference anywhere upstream is enough to flip that choice, and after the flip the two texts continue from different prefixes, so they diverge completely. This is expected behaviour, and you will see it again in Lesson 15 (batched decoding) and Lesson 19 (speculative decoding), where a different kernel shape changes the rounding. The test is always the same: at the first divergent token, are the top two logits within a step or two? If yes, it is a near-tie; if no, it is a bug.

Turn it into tests

Comparisons against Python are a development tool; you do not want Python in your test suite. What you can keep is self-consistency tests that encode the same tolerance. For example, decoding several prompts as one batch must match decoding each alone:

code/Tests/InferenceTests/BatchTests.swiftswift
func batchedDecodeMatchesSerial(_ which: String) throws {
    let found = which == "qwen3" ? TestModels.qwen3 : TestModels.qwen35
    try #require(found != nil, "model weights for \(which) not found")
    let dir = found!
    let model: any LanguageModel = which == "qwen3" ? try loadQwen3(from: dir) : try loadQwen35(from: dir, withMTP: false)
    let prompts: [[Int]] = [[9707, 11, 1246, 525], [785, 6722, 315, 9625, 374], [16, 11, 17, 11, 18, 11]]
    let steps = 24

    // Serial reference: logits for each step of each prompt.
    var serial = [[MLXArray]]()
    for p in prompts {
        let caches = model.makeCaches()
        var logits = model(MLXArray(p.map(Int32.init)).reshaped(1, -1), caches: caches)[0..., -1, 0...]
        var rows = [logits]
        for _ in 1 ..< steps {
            let t = argMax(logits, axis: -1).reshaped(1, 1)
            logits = model(t, caches: caches)[0..., -1, 0...]
            rows.append(logits)
        }
        eval(rows)
        serial.append(rows)
    }

The full test then decodes the same prompts in a batch and requires every logit to be within 1.0 of the serial run, for both Qwen3 and Qwen3.5. It runs in about 8 seconds. The model-backed tests look for the checkpoints in the Hugging Face cache, or in paths given by environment variables, and fail with a clear message if the weights are missing.

The same method checked every architecture in this course against the reference before any lesson was written: Qwen3 (above), Qwen3.5 (same top token at every position, differences up to 0.58 at logits around 23), and the mixture-of-experts variants in Lesson 16.

Lesson in one breath

Compare logits, not text. Pin the reference to the same MLX core version. In bfloat16, expect exact agreement for the first position and last-digit differences elsewhere, with the same top token everywhere. When logits differ more than that, compare layer by layer to find the first divergence. When greedy output diverges after many identical tokens, check whether the top two logits were within one bfloat16 step.

Exercise 1compute it

bfloat16 has 8 bits of precision (7 stored plus 1 implicit). What is the gap between adjacent bfloat16 values just above 16? (Hint: between 16 and 32 there are 128 values.)

16 / 128 = 0.125. Between 2n and 2n+1 there are 128 evenly spaced values, so the step is 2n / 128.

Exercise 2one answer

Your logits match exactly at position 0 and differ by a few bfloat16 steps elsewhere, with the same argmax everywhere. Where would a real bug most likely be, if there is one?

Position 0 attends only to itself and RoPE at position 0 is the identity. Everything per-position is therefore verified; only cross-position computation is left.

Exercise 3one answer

Greedy outputs are identical for 120 tokens and then diverge. At the divergence, the reference's top two logits are 18.50 and 12.25. What does this suggest?

Rounding moves logits by a step or two (0.0625 to 0.125 here). A gap of 6.25 means the two implementations computed materially different things at that point, for example a cache or position bug that only appears at long context.

Exercise 4one answer

Why pin the Python reference to the same MLX core version as the Swift package?

You want the comparison to isolate your code. Version drift adds its own small differences.
