6. Tokenizer and chat template

The model only sees integers. Turn chat messages into exactly the token sequence Qwen was trained on, and turn generated tokens back into text that can be streamed safely.

By the end of this lesson you can

  • Explain what the tokenizer files contain and which library uses them
  • Render a conversation with Qwen's chat template, with and without thinking
  • Choose the right set of end-of-sequence tokens
  • Stream text from tokens without breaking multi-byte characters
  • Implement stop strings that never leak a partial match

From text to ids

Qwen uses byte-level BPE: text is turned into UTF-8 bytes, and frequent byte sequences are merged into tokens according to the rules in tokenizer.json. Common words are one token, rare words several, and any byte sequence at all can be encoded, so there is no "unknown" token. Qwen3 has a vocabulary of 151,936 entries; Qwen3.5 has 248,320.

A few tokens are special: they are never produced by splitting ordinary text, and they carry structure.

TokenId (Qwen3)Meaning
<|endoftext|>151643end of a document in pretraining
<|im_start|>151644start of a chat turn
<|im_end|>151645end of a chat turn
<think>, </think>151667, 151668wrap the model's reasoning

You do not implement BPE yourself. The Tokenizers library from swift-transformers reads the same files as Python's transformers and produces identical ids. AutoTokenizer.from(modelFolder:) loads it from the checkpoint folder.

The chat template

A chat model was fine-tuned on conversations in one exact format, and it only behaves well if you reproduce that format to the byte. The format is stored with the model, in tokenizer_config.json (or chat_template.jinja), as a Jinja template. For Qwen it is ChatML. One user message renders as:

<|im_start|>user
Why is the sky blue?<|im_end|>
<|im_start|>assistant
<think>

</think>

The prompt ends at the start of the assistant's turn, and the model continues from there. The empty <think> block is what enable_thinking: false produces: Qwen3 and Qwen3.5 are hybrid reasoning models, and an already-closed think block tells them to answer directly. With thinking enabled, the template stops after assistant\n, and the model writes its reasoning inside <think>...</think> before the answer.

Our wrapper passes the messages, the tools (Lesson 21) and the thinking flag straight to the template engine:

code/Sources/Inference/LoadedModel.swiftswift
/// Formats a conversation, and the tools the model may call, with the
/// model's chat template.
public func prompt(
    messages: [[String: any Sendable]], tools: [[String: any Sendable]]? = nil, enableThinking: Bool = false
) throws -> [Int] {
    try tokenizer.applyChatTemplate(
        messages: messages, tools: tools, additionalContext: ["enable_thinking": enableThinking])
}

For the example above this produces the 18 ids [151644, 872, 198, 10234, 374, 279, 12884, 6303, 30, 151645, 198, 151644, 77091, 198, 151667, 271, 151668, 271], the same ids Python's apply_chat_template produces. Comparing the two is the first test to write for any new model: a wrong template does not crash, it just makes the model quietly worse.

When to stop

Generation stops when the model emits an end token. Which one? config.json names one eos_token_id, but in practice a chat model ends a turn with <|im_end|>, a base model ends a document with <|endoftext|>, and a fine-tune sometimes uses either. The loader collects all of them into a set:

code/Sources/Inference/LoadedModel.swiftswift
// Chat models end a turn with <|im_end|>; base models with <|endoftext|>.
let eos = Set([tokenizer.eosTokenId,
               tokenizer.convertTokenToId("<|im_end|>"),
               tokenizer.convertTokenToId("<|endoftext|>")].compactMap { $0 })

Checking membership in this set after every token is cheap, and stopping one token too late is far more visible to users (the model starts writing the next user turn) than any cost of the check.

Streaming text from tokens

Streaming means sending text after every token. The obvious approach, decoding each token on its own and sending the result, breaks in two ways:

  • Multi-byte characters. Byte-level BPE can split one character across tokens. An emoji is four UTF-8 bytes and may arrive as two tokens; decoding the first alone gives the replacement character U+FFFD (�).
  • Context-dependent spacing. Some tokenizers decide how a token prints based on its neighbours, so decoding tokens one by one does not always concatenate to the decoding of the whole sequence.

The fix is to decode a window of recent tokens, emit only the part of the text that is new, and wait if the text ends in U+FFFD:

code/Sources/Inference/Detokenizer.swiftswift
/// Turns a growing list of token ids into text increments.
///
/// One token is not always one piece of text: a multi-byte character can
/// span tokens, and the tokenizer may change how earlier tokens print once
/// it sees the next one. So we decode a window of recent tokens and emit
/// only what is new, holding back a trailing U+FFFD (an incomplete
/// character). The window restarts after each newline to keep decoding cheap.
public struct StreamingDetokenizer {
    let tokenizer: any Tokenizer
    var tokens: [Int] = []
    var segmentStart = 0
    var emitted = ""

    public init(tokenizer: any Tokenizer) {
        self.tokenizer = tokenizer
    }

    public mutating func append(_ token: Int) -> String {
        tokens.append(token)
        let text = tokenizer.decode(tokens: Array(tokens[segmentStart...]))
        if text.hasSuffix("\u{FFFD}") { return "" }
        let delta = String(text.dropFirst(emitted.count))
        emitted = text
        if text.hasSuffix("\n") {
            segmentStart = tokens.count
            emitted = ""
        }
        return delta
    }
}

Decoding the whole output after every token would be correct but quadratic in length. Restarting the window after each newline keeps the work per token small, because a newline is a safe boundary for every tokenizer in this course.

Stop strings

Clients can ask generation to stop at strings such as "\n\nUser:". The difficulty is the same as above, one level up: a stop string can arrive split over several tokens. If you stream "\n\nUs" and only then see "er:", the client already has text it should never have received.

So the matcher holds back any suffix of the pending text that could still become a stop string, and releases it as soon as it cannot:

code/Sources/Inference/Detokenizer.swiftswift
/// Watches streamed text for stop strings. Text that might be the start of
/// a stop string is held back until it is clear either way.
public struct StopMatcher {
    let stops: [String]
    var pending = ""

    public init(stops: [String]) {
        self.stops = stops.filter { !$0.isEmpty }
    }

    /// Returns text that is safe to emit, and whether a stop string was hit.
    public mutating func feed(_ text: String) -> (String, stopped: Bool) {
        pending += text
        for stop in stops {
            if let range = pending.range(of: stop) {
                let out = String(pending[..<range.lowerBound])
                pending = ""
                return (out, true)
            }
        }
        // Keep the longest suffix that is a prefix of some stop string.
        var keep = 0
        for stop in stops {
            for n in stride(from: min(stop.count - 1, pending.count), to: 0, by: -1)
            where pending.hasSuffix(stop.prefix(n)) {
                keep = max(keep, n)
                break
            }
        }
        let out = String(pending.dropLast(keep))
        pending = String(pending.suffix(keep))
        return (out, false)
    }

    /// Flushes held-back text once generation ends for another reason.
    public mutating func finish() -> String {
        defer { pending = "" }
        return pending
    }
}

The unit tests in Tests/InferenceTests/TextTests.swift pin both behaviours: "hello E" + "N" + "D tail" with stop "END" emits only "hello ", and "an E" + "xit" releases the held-back "E" once "Ex" rules out "END". When generation ends for any other reason, the engine calls finish() to flush whatever was held back.

Lesson in one breath

swift-transformers loads the tokenizer and renders the Jinja chat template stored in the checkpoint. Qwen uses ChatML: each turn is wrapped in <|im_start|>role … <|im_end|>, and a turn ends when the model emits <|im_end|>. Streaming needs care because one token is not one character: decode a window, hold back incomplete characters, and hold back text that could be the start of a stop string.

Exercise 1one answer

Your server renders prompts with a hand-written template that differs from Qwen's by one newline. What happens?

Nothing checks the format. The model sees an input slightly outside what it was tuned on and degrades without any error, which is why the template from the checkpoint should always be used.

Exercise 2type the term

Which special token does a Qwen chat model emit to end its turn?

ChatML closes every turn with <|im_end|>. <|endoftext|> ends a pretraining document and is kept in the stop set for base models.

Exercise 3one answer

The detokenizer decodes the window and gets text ending in U+FFFD. What should it do?

U+FFFD at the end means the bytes so far do not complete a character. The next token will, and the full character goes out then.

Exercise 4one answer

Stop string "STOP". The stream so far is "ok ST". What may be sent to the client right now?

"ST" is a prefix of "STOP", so it must be held back until the next text shows whether the stop string completes.

Exercise 5one answer

Why does the chat template append an empty <think>\n\n</think> when thinking is disabled?

Hybrid reasoning models were trained to reason inside think tags. A closed, empty block is the trained signal for "no reasoning, answer now".
