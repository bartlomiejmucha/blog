Arrays, shapes and broadcasting

An MLXArray is an n-dimensional array with a shape and a dtype. If you have used NumPy or PyTorch, the operations will look familiar:

code/Sources/mlx-basics/main.swiftswift
func arraysAndShapes() {
    let a = MLXArray([1, 2, 3, 4, 5, 6] as [Float]).reshaped(2, 3)
    print(a.shape, a.dtype)              // [2, 3] float32

    let b = MLXArray([10, 20, 30] as [Float])
    print(a + b)                          // b is broadcast across both rows

    let m = MLXArray.ones([3, 4])
    print(matmul(a, m).shape)             // [2, 4]

    print(a[0])                           // first row
    print(a[0..., 1])                     // second column
    print(a[.ellipsis, ..<2])             // first two columns
}

Two rules carry most of the weight:

  • Broadcasting. When shapes differ, size-1 or missing leading dimensions are stretched to match. [2, 3] + [3] adds the vector to each row. Models use this constantly: adding a bias, scaling by a norm weight.
  • Indexing. a[0..., 1] means "all rows, column 1"; .ellipsis stands for "all leading dimensions", so x[.ellipsis, ..<2] takes the first two entries of the last axis whatever the rank. Negative indices count from the end: logits[0..., -1, 0...] is the last position of every sequence, which you will write in every generation loop.

Model tensors in this course follow one convention: [B, L, D] for activations (batch, sequence length, hidden size) and [B, heads, L, headDim] inside attention.

dtypes: why bfloat16

code/Sources/mlx-basics/main.swiftswift
func dtypes() {
    let x = MLXArray([1.5, -2.25, 3.0] as [Float])
    let h = x.asType(.bfloat16)
    print(h.dtype, h.nbytes)              // bfloat16, 6 bytes: 2 per element
    // bfloat16 keeps float32's range but only ~3 significant digits.
    print(MLXArray(Float(1000.1)).asType(.bfloat16).item(Float.self))  // 1000.0
}

Model weights and activations are usually stored in bfloat16: 16 bits with float32's 8-bit exponent but only 7 bits of mantissa. It covers the same range as float32, so huge or tiny values do not overflow, but it keeps only about three significant decimal digits: 1000.1 becomes 1000.0.

Half the bytes means half the memory traffic, and Lesson 2 showed that memory traffic is the speed limit. The cost is precision, and you will meet it again: when comparing your model with the Python reference, differences show up in the last bfloat16 digit, and occasionally flip which of two near-equal tokens wins (Lesson 8). Places where precision matters, such as softmax and the linear-attention state, compute in float32 and convert back.

Lazy evaluation

This is the most important idea in MLX. Operations do not compute anything when you call them. They record a node in a graph and return immediately. The work runs when a result is actually needed:

code/Sources/mlx-basics/main.swiftswift
func lazyEvaluation() {
    let a = MLXArray.ones([4096, 4096])
    eval(matmul(a, a))                    // warm up: the first call also sets up kernels
    let t0 = Date()
    let b = matmul(a, a) + 1              // builds a graph; nothing runs yet
    let built = Date()
    eval(b)                               // now the GPU does the work
    let done = Date()
    print(String(format: "build %.3f ms, eval %.1f ms",
                 built.timeIntervalSince(t0) * 1000, done.timeIntervalSince(built) * 1000))
    // item() and printing also force evaluation.
    print(b[0, 0].item(Float.self))       // 4097.0
}

On the M1 this prints about build 0.04 ms, eval 94 ms: building the graph for a 4096×4096 matrix multiply is instant, and the GPU work happens inside eval. Evaluation is triggered by

  • eval(...), explicitly;
  • item(), which reads a scalar back to Swift;
  • printing an array.

Laziness lets MLX fuse and schedule work, and it lets you build a whole forward pass before anything runs. It also has two traps. First, a graph that is never evaluated keeps growing: in a generation loop you must eval the caches regularly, or each step drags the entire history along. Second, a stray item() in a hot loop forces the CPU to wait for the GPU at that point. Lesson 19 finds exactly this bug in the speculative decoder and removes three of its four waits.

Asynchronous evaluation

code/Sources/mlx-basics/main.swiftswift
func asyncEvaluation() {
    let a = MLXArray.ones([2048, 2048])
    var x = a
    for _ in 0 ..< 3 { x = matmul(x, a) / 2048 }
    asyncEval(x)                          // queue the work and return at once
    // ... the CPU is free to prepare the next step here ...
    print(x[0, 0].item(Float.self))       // blocks only if the GPU is not done yet
}

asyncEval starts evaluating and returns at once. The CPU can keep working, usually building the graph for the next step, while the GPU computes. Reading the result later blocks only if the GPU has not finished.

The generation loop in Lesson 9 is built around this. Before handing token n to the caller, it queues the forward pass for token n+1, so the CPU-side work of detokenizing and streaming token n overlaps with GPU work. On the M1 that saves about 1.2 ms per token, roughly 11%, measured in Lesson 20.

Measure Release builds only

MLX's C++ core is compiled as part of your package. In a Debug build it is compiled without optimization, and the CPU side of every operation, from building graphs to dispatching kernels, becomes several times slower. On the M1 the same Qwen3.5 decode runs at 36 tokens per second in Debug and 89 in Release.

The GPU kernels are identical in both, so Debug builds are fine for checking correctness. But every speed number in this course comes from a Release build, and any number you measure should too. While writing this course, early speculative-decoding results that looked like a 1.4× win in Debug turned out to be a slowdown in Release, because Debug overhead had hidden what the GPU was really doing.

Lesson in one breath

MLX arrays are lazy: operations record a graph, and work happens on eval, item, or printing. asyncEval starts the work without waiting, which lets the CPU prepare the next step while the GPU runs. Build with xcodebuild so the Metal shaders are compiled, and measure only Release builds.

Exercise 3compute it

An array of 1,000,000 bfloat16 values. How many megabytes is it (1 MB = 106 bytes)?

bfloat16 is 2 bytes per value: 2,000,000 bytes = 2 MB. In float32 it would be 4 MB.

Exercise 4one answer

A generation loop appends to a KV cache every step but never calls eval on it. What goes wrong?

Unevaluated arrays are graphs. Without regular evaluation the cache becomes a chain of every update ever made.

Exercise 5one answer

Why measure performance only on Release builds?

The Metal kernels are the same; the C++ code that builds and dispatches them is much slower unoptimized. Debug timings mostly measure that overhead.
