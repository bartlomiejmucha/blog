11. An OpenAI-compatible API with Hummingbird

Put an HTTP front on the engine that speaks the Chat Completions wire format, so every existing OpenAI client and SDK can use your server unchanged.

By the end of this lesson you can

  • Set up a Hummingbird router with health, models and chat completion routes
  • Decode the Chat Completions request, including fields clients send in several shapes
  • Encode responses in the exact JSON shape clients expect
  • Return useful errors instead of crashing on bad input

Why the OpenAI format

You could invent your own API. Don't. The Chat Completions format has become the common language of LLM servers: the official OpenAI SDKs, LangChain, editor plugins and countless scripts all speak it, and they only need a different base URL to talk to yours. Matching it costs a few Codable structs.

The server needs four routes:

RoutePurpose
GET /healthliveness check for scripts and load balancers
GET /v1/modelslists the model id; many clients call it on startup
POST /v1/chat/completionsthe real work, streaming or not
GET /metricsPrometheus counters (Lesson 21)

let args = CommandLine.arguments
func option(_ name: String) -> String? {
    args.firstIndex(of: name).flatMap { args.indices.contains($0 + 1) ? args[$0 + 1] : nil }
}
let directory = URL(filePath: args[1])
let port = Int(option("--port") ?? "") ?? 8080
let batchSize = Int(option("--batch") ?? "") ?? 1

let bits = Int(option("--bits") ?? "") ?? 4
let loaded = try await LoadedModel.load(directory: directory, name: option("--name"), quantizeBits: bits == 16 ? nil : bits)
let engine: any InferenceEngine = batchSize > 1
    ? BatchEngine(loaded: loaded, maxBatch: batchSize)
    : SerialEngine(loaded: loaded, useMTP: !args.contains("--no-mtp"))
let modelName = loaded.name
let formatter = PromptFormatter(loaded)
let metrics = Metrics()
print("loaded \(modelName), listening on 127.0.0.1:\(port)")

Startup loads the model once, picks an engine (the serial engine with MTP by default, or the batching engine of Lesson 15), and creates the shared objects the routes use. Everything here is created before the server accepts its first connection, so no request ever waits for a model to load.

A Hummingbird route is an async closure that receives the request and a context and returns anything that can become a response: a String, or a Response you build yourself. The application at the bottom of the file binds to localhost:

code/Sources/serve/main.swiftswift
let app = Application(router: router, configuration: .init(address: .hostname("127.0.0.1", port: port)))
try await app.runService()

Binding to 127.0.0.1 keeps the server off the network. It has no authentication, so exposing it is a deliberate decision, not a default (Lesson 21).

Decoding the request

code/Sources/serve/OpenAI.swiftswift
/// Scalar request fields. `messages` and `tools` are read separately as
/// untyped JSON, because they go straight into the chat template.
struct ChatRequest: Decodable {
    var model: String?
    var stream: Bool?
    var temperature: Float?
    var topP: Float?
    var topK: Int?
    var minP: Float?
    var seed: UInt64?
    var maxTokens: Int?
    var maxCompletionTokens: Int?
    var stop: Stop?
    var enableThinking: Bool?

    /// `stop` may be a single string or a list of strings.
    enum Stop: Decodable {
        case one(String)
        case many([String])

        init(from decoder: Decoder) throws {
            let c = try decoder.singleValueContainer()
            if let s = try? c.decode(String.self) { self = .one(s) } else { self = .many(try c.decode([String].self)) }
        }

        var list: [String] {
            switch self {
            case .one(let s): [s]
            case .many(let l): l
            }
        }
    }
}

Two details worth copying:

  • Snake case without coding keys. The shared decoder uses convertFromSnakeCase, so max_completion_tokens lands in maxCompletionTokens. The encoder does the reverse for responses.
  • Fields with several shapes. OpenAI accepts stop as a string or a list. A small enum with a custom init(from:) accepts both. Clients rely on such details, and a strict decoder that rejects a valid request is a compatibility bug.

messages and tools are not in this struct. Their contents go straight into the Jinja chat template, which wants untyped dictionaries, and modelling every possible message shape (text, tool calls, tool results, image parts) in Swift types would only be converted back again. The route reads them separately with JSONSerialization:

code/Sources/serve/main.swiftswift
router.post("v1/chat/completions") { request, context -> Response in
    let body = try await request.body.collect(upTo: 4 << 20)
    let chat: ChatRequest
    let messages: [[String: Any]]
    let tools: [[String: Any]]?
    do {
        chat = try jsonDecoder.decode(ChatRequest.self, from: body)
        let raw = try JSONSerialization.jsonObject(with: Data(buffer: body)) as? [String: Any] ?? [:]
        guard let m = raw["messages"] as? [[String: Any]], !m.isEmpty else { throw ServeError.noMessages }
        messages = m
        tools = raw["tools"] as? [[String: Any]]
    } catch {
        return try json(ErrorBody(error: .init(message: "\(error)", type: "invalid_request_error")), status: .badRequest)
    }

    let prompt = try formatter.render(
        messages: messages.map(templateMessage),
        tools: tools?.map { $0.mapValues(sendableJSON) },
        enableThinking: chat.enableThinking ?? false)
    let expectTools = !(tools ?? []).isEmpty
    let generation = GenerationRequest(
        prompt: prompt,
        parameters: SamplingParameters(
            temperature: chat.temperature ?? 0.7, topK: chat.topK ?? 0, topP: chat.topP ?? 1,
            minP: chat.minP ?? 0, seed: chat.seed),
        maxTokens: chat.maxCompletionTokens ?? chat.maxTokens ?? 512,
        stop: chat.stop?.list ?? [])

The body size is capped at 4 MB before anything is parsed, malformed JSON or an empty message list returns HTTP 400 with an OpenAI-style error body, and missing sampling fields get defaults. The result is a GenerationRequest: token ids, sampling parameters, a token limit and stop strings. That is everything the engine needs, and nothing about HTTP.

Submitting and answering

code/Sources/serve/main.swiftswift
let submitted: AsyncThrowingStream<GenerationEvent, Error>
do {
    submitted = try engine.submit(generation)
} catch EngineError.queueFull {
    metrics.update { $0.rejected += 1 }
    return try json(ErrorBody(error: .init(message: "server busy, retry later", type: "rate_limit")), status: .tooManyRequests)
}

let id = "chatcmpl-" + UUID().uuidString.prefix(12).lowercased()
let created = Int(Date().timeIntervalSince1970)
let events = instrument(submitted)

engine.submit returns immediately with an AsyncThrowingStream of events: text pieces, then one .finished with the reason and token counts. If the engine's queue is full it throws, and the client gets HTTP 429 at once. instrument wraps the stream to record metrics (Lesson 21).

A non-streaming request simply collects the stream:

code/Sources/serve/main.swiftswift
var text = ""
var finish = FinishReason.length
var usage = Usage(promptTokens: 0, completionTokens: 0, cachedTokens: 0)
for try await event in events {
    switch event {
    case .text(let t): text += t
    case .finished(let r, let u): finish = r; usage = u
    }
}
let (content, calls) = expectTools ? ToolCallParser.parse(text) : (text, [])
return try json(ChatCompletion(
    id: id, created: created, model: modelName,
    choices: [.init(
        message: .init(role: "assistant", content: calls.isEmpty ? text : content,
                       toolCalls: calls.isEmpty ? nil : toolCallBodies(calls)),
        finishReason: calls.isEmpty ? finish.rawValue : "tool_calls")],
    usage: usageBody(usage)))

and encodes it in the response shape clients expect:

code/Sources/serve/OpenAI.swiftswift
struct ChatCompletion: Encodable {
    struct Choice: Encodable {
        var index = 0
        var message: ChatMessage
        var finishReason: String
    }
    var id: String
    var object = "chat.completion"
    var created: Int
    var model: String
    var choices: [Choice]
    var usage: UsageBody
}
code/Sources/serve/main.swiftswift
func json(_ value: some Encodable, status: HTTPResponse.Status = .ok) throws -> Response {
    Response(status: status, headers: [.contentType: "application/json"],
             body: ResponseBody(byteBuffer: ByteBuffer(data: try jsonEncoder.encode(value))))
}

The finish_reason values matter to clients: stop means the model ended its turn or hit a stop string, length means the token limit cut it off, and tool_calls means the model wants a function called. usage.prompt_tokens_details.cached_tokens reports how much of the prompt the cache covered (Lesson 14).

Try it with an SDK

from openai import OpenAI
client = OpenAI(base_url="http://localhost:8080/v1", api_key="unused")
reply = client.chat.completions.create(
    model="qwen3.5-0.8b",
    messages=[{"role": "user", "content": "One sentence on unified memory."}],
    temperature=0,
)
print(reply.choices[0].message.content)

The SDK requires an API key and a model name; the server ignores both. Everything else, including streaming in the next lesson, works without changes.

Lesson in one breath

Hummingbird maps routes to async closures. The chat route decodes the request, renders the prompt, submits a GenerationRequest to the engine, and either streams or collects the resulting events. Snake-case JSON strategies keep the Swift types idiomatic while matching OpenAI's field names exactly.

Practice

Answers are checked in your browser and saved to this device. Get one wrong and you can retry as many times as you like.

Exercise 1one answer

A client sends "stop": "###" and your decoder only accepts arrays. What happens?

Codable is strict about types. Accepting every shape the official API accepts is part of being compatible.

Exercise 2one answer

Why does the route read messages with JSONSerialization instead of a Codable struct?

Messages can contain text, tool calls, tool results and more. Passing them through untouched supports all of them with no extra code.

Exercise 3type the term

Which finish_reason tells a client that generation was cut off by the token limit?

length. Clients often show a "continue" option when they see it.

Exercise 4one answer

Why does the server bind to 127.0.0.1 by default?

Anyone who can reach an unauthenticated inference server can use your GPU. Listening on localhost only is the safe default.
