15. Continuous batching

Serve several sequences in each decode step so the weights are read once for all of them. Build a batching engine without padding, then measure how much it really helps on an M1, and why the answer depends on the matmul kernel.

By the end of this lesson you can

  • Explain why batching raises throughput for memory-bound decoding
  • Build batch views over per-sequence caches for both attention and linear attention
  • Interleave chunked prefill with batched decode
  • Read measured batching curves and connect them to kernel behaviour
  • Explain why batched outputs differ slightly from unbatched ones

Why batching works

Go back to Lesson 2's table. One sequence decoding at 4 bits does about 4 operations per weight byte, far below the M1's balance point of about 24. The GPU spends most of the step waiting for weights. If eight sequences each need one token, their eight token vectors can be stacked into an 8-row matrix and multiplied by each weight matrix in one pass. The weights are read once, the arithmetic goes up eightfold, and the step should cost little more than a single-sequence step.

"Continuous" means the batch changes all the time. Requests finish at different moments and new ones arrive. Instead of waiting for a whole batch to finish, the engine admits and retires sequences between any two steps.

Batch views instead of padding

The hard part is that sequences have different lengths. The common solution is to pad all caches to the longest one and mask the padding. This course uses a simpler design that needs no padding at all:

  • Matmuls run batched. The new tokens of all sequences form a [B, 1] input, so every projection and MLP sees a [B, 1, hidden] activation. This is where the weight reads, and therefore nearly all of the cost, happen.
  • Attention runs per sequence. Each sequence's keys and values stay in its own cache, at its own length, with its own RoPE offset. A BatchKVCache view tells attend to process the rows one at a time:

/// The attention caches of several independent sequences, used for one
/// batched decode step. Each sequence keeps its own length and positions.
final class BatchKVCache: LayerCache {
    let caches: [KVCache]
    init(_ caches: [KVCache]) { self.caches = caches }
    var offset: Int { caches.map(\.offset).max() ?? 0 }
    var state: [MLXArray] { caches.flatMap(\.state) }
    func trim(_ count: Int) { caches.forEach { $0.trim(count) } }
    func copy() -> LayerCache { fatalError("batch views are temporary") }
}

Qwen3.5's linear-attention layers are even easier, because every sequence's state has the same fixed size. A BatchLinearCache stacks the states along the batch axis for the step and splits the results back:

code/Sources/Inference/LayerCache.swiftswift
/// The linear-attention state of several sequences, stacked along the batch
/// axis for one step and split back afterwards. Every sequence holds the
/// same fixed-size state, so no padding is needed.
final class BatchLinearCache: LayerCache {
    let caches: [LinearCache]
    init(_ caches: [LinearCache]) { self.caches = caches }
    var offset: Int { caches.map(\.offset).max() ?? 0 }
    var state: [MLXArray] { caches.flatMap(\.state) }
    func trim(_ count: Int) { caches.forEach { $0.trim(count) } }
    func copy() -> LayerCache { fatalError("batch views are temporary") }

    var conv: MLXArray { concatenated(caches.map { $0.conv! }, axis: 0) }
    var recurrent: MLXArray { concatenated(caches.map { $0.recurrent! }, axis: 0) }

    func update(conv: MLXArray, recurrent: MLXArray, count: Int) {
        for (i, cache) in caches.enumerated() {
            cache.update(conv: conv[i ..< i + 1], recurrent: recurrent[i ..< i + 1], count: count, snapshots: [])
        }
    }
}

The model code needs no other change. A helper builds one view per layer from the per-sequence caches:

code/Sources/Inference/LayerCache.swiftswift
/// Per-layer views that span the caches of several sequences.
public func batchCaches(_ perSequence: [[LayerCache]]) -> [LayerCache] {
    (0 ..< perSequence[0].count).map { layer in
        if perSequence[0][layer] is KVCache {
            return BatchKVCache(perSequence.map { $0[layer] as! KVCache })
        }
        return BatchLinearCache(perSequence.map { $0[layer] as! LinearCache })
    }
}

The per-row attention costs a few extra kernel launches per layer. The measurements below show it is small: in bfloat16, going from 4 to 8 rows adds only 7 ms per step.

The batching engine

The engine keeps the same inbox and worker thread as the serial engine, but its loop does three things per iteration: admit new jobs, advance at most one prefill chunk, and run one batched decode step for every running sequence.

code/Sources/Inference/BatchEngine.swiftswift
private func run() {
    while true {
        if waiting.isEmpty && running.isEmpty { wake.wait() }
        for job in inbox.withLock({ q in defer { q.removeAll() }; return q }) {
            waiting.append(Sequence(job: job, loaded: loaded))
        }

        // Drop sequences whose clients went away.
        for s in (waiting + running) where s.job.cancelled {
            finish(s, .cancelled)
        }

        // Admit: advance the oldest waiting prompt by one chunk.
        if running.count < maxBatch, let s = waiting.first {
            prefillChunk(s)
        }

        if !running.isEmpty {
            decodeStep()
        }
    }
}
code/Sources/Inference/BatchEngine.swiftswift
private func prefillChunk(_ s: Sequence) {
    let chunk = s.pendingPrompt.prefix(prefillChunk)
    s.pendingPrompt = s.pendingPrompt.dropFirst(chunk.count)
    let logits = loaded.model(MLXArray(chunk.map(Int32.init)).reshaped(1, -1), caches: s.caches)
    if s.pendingPrompt.isEmpty {
        // The prompt is done: its last logits give the first token.
        let token = s.sampler(logits[0..., -1, 0...])
        eval(token)
        waiting.removeFirst()
        running.append(s)
        emit(s, token.item(Int.self))
    } else {
        eval(s.caches.flatMap(\.state))
    }
}
code/Sources/Inference/BatchEngine.swiftswift
private func decodeStep() {
    let batch = running
    let tokens = MLXArray(batch.map { Int32($0.last) }).reshaped(batch.count, 1)

    // One cache view per layer that spans every running sequence.
    let caches = batchCaches(batch.map(\.caches))

    let logits = loaded.model(tokens, caches: caches)
    let next = batch.indices.map { i in batch[i].sampler(logits[i ..< i + 1, -1, 0...]) }
    eval(next)
    for (s, token) in zip(batch, next) {
        emit(s, token.item(Int.self))
    }
}

Chunked prefill is the key scheduling decision. A new 2,000-token prompt prefilled in one go would freeze every running sequence for its whole duration. Prefilling 256 tokens per loop iteration instead, between decode steps, means running sequences slow down while a newcomer is admitted, but never stop. Each sequence samples with its own parameters and its own random key, so a greedy request and a creative one can share a batch.

What it buys on an M1

Here is the decode step time for Qwen3.5-0.8B at batch sizes 1 to 8, Release build, base M1:

              B=1        B=2        B=4        B=8
4-bit       11.8 ms    19.0 ms    34.9 ms    63.9 ms     → 85, 105, 115, 125 tok/s total
8-bit       18.5 ms    22.2 ms    31.8 ms    60.3 ms     → 54,  90, 126, 133 tok/s total
bf16        31.5 ms    66.5 ms    69.7 ms    76.5 ms     → 32,  30,  57, 105 tok/s total

Batching helps, but nowhere near the eightfold the theory suggested, and the shape of the curve depends on the precision. The cause is the matrix multiply kernel, measured in isolation on a 14336×1024 weight:

rows     4-bit       8-bit       bf16
1        142 µs      266 µs      482 µs
2        248 µs      266 µs     1225 µs
4        489 µs      428 µs     1223 µs
8        831 µs      833 µs     1227 µs

MLX picks a different kernel for one row (a matrix-vector kernel that streams the weights at about 52 GB/s, near the M1's limit) and for several rows. For 4-bit weights on this GPU, the multi-row path's cost grows almost linearly from 2 to 8 rows, so batching barely amortizes anything. For 8-bit weights, two rows cost the same as one. For bfloat16, the first extra row costs 2.5×, but then 8 rows cost the same as 2. The chart below plots the measured curves.

The lesson is not "batching does not work". It is that the benefit is a property of the kernels on your hardware, and you must measure it. On chips with more compute per byte, or with newer MLX kernels, the curve is flatter. Lesson 19 runs into the same table from another direction: speculative decoding is also a multi-row multiply.

Batching changes the numbers

Running the same eight greedy requests through the serial engine and the batching engine produced identical text for only one of the eight. Is batching broken?

No. The batched test from Lesson 8 shows logits within tolerance at every step. The multi-row kernel accumulates its sums in a different order than the one-row kernel, so values differ in the last bfloat16 digit, and somewhere in 128 tokens a near-tie flips (Lesson 8). After that, the texts diverge. This is called the batch invariance problem: a request's output depends on what else is in the batch. It matters if users expect bit-reproducible results with a seed; kernels that are batch-invariant by design exist, at some cost in speed.

Lesson in one breath

A decode step's cost is dominated by reading the weights, so running B sequences in one step multiplies useful work by up to B. The engine keeps each sequence's own caches, stacks the token rows for every matmul, and runs attention per sequence. Linear-attention states are stacked along the batch axis. New prompts are prefilled one chunk per loop. On an M1 the gain is real but limited, because MLX's quantized matmul kernel gets slower per row between 2 and 8 rows; and batching changes rounding enough to flip near-ties.
