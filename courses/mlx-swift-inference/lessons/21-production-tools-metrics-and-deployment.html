Tool calling

A client describes functions the model may call; the model decides to call one by emitting a structured block instead of text; the client runs the function and sends the result back as a tool message. The server's part is to render the tools into the prompt and recognize calls in the output.

Rendering is done by the chat template, which already knows the model's trained format. Qwen3.5's template, for instance, lists the tools as JSON inside <tools> and instructs the model to reply with:

<tool_call>
<function=get_weather>
<parameter=city>
Oslo
</parameter>
</function>
</tool_call>

Qwen3 uses JSON inside the same tags: <tool_call>{"name": "get_weather", "arguments": {"city": "Oslo"}}</tool_call>. The parser accepts both:

code/Sources/Inference/ToolCalls.swiftswift
/// Extracts tool calls from model output.
///
/// Qwen models write calls inside `<tool_call>...</tool_call>`. Qwen3 puts
/// JSON inside (`{"name": ..., "arguments": {...}}`); Qwen3.5 uses XML-like
/// tags (`<function=name><parameter=key>value</parameter></function>`).
/// Both are accepted. Text before the first call is returned as content.
public enum ToolCallParser {
    public static let openTag = "<tool_call>"
    static let closeTag = "</tool_call>"

    public static func parse(_ text: String) -> (content: String, calls: [ToolCall]) {
        guard let first = text.range(of: openTag) else { return (text, []) }
        let content = String(text[..<first.lowerBound]).trimmingCharacters(in: .whitespacesAndNewlines)
        var calls = [ToolCall]()
        var rest = text[first.lowerBound...]
        while let open = rest.range(of: openTag) {
            let afterOpen = rest[open.upperBound...]
            let close = afterOpen.range(of: closeTag)
            let body = String(close.map { afterOpen[..<$0.lowerBound] } ?? afterOpen)
            if let call = parseJSON(body) ?? parseXML(body) { calls.append(call) }
            guard let close else { break }
            rest = afterOpen[close.upperBound...]
        }
        return (content, calls)
    }

    static func parseJSON(_ body: String) -> ToolCall? {
        guard let data = body.trimmingCharacters(in: .whitespacesAndNewlines).data(using: .utf8),
              let object = try? JSONSerialization.jsonObject(with: data) as? [String: Any],
              let name = object["name"] as? String
        else { return nil }
        let args = object["arguments"] ?? [String: Any]()
        let encoded = (try? JSONSerialization.data(withJSONObject: args, options: [.sortedKeys])) ?? Data("{}".utf8)
        return ToolCall(name: name, arguments: String(decoding: encoded, as: UTF8.self))
    }

    static func parseXML(_ body: String) -> ToolCall? {
        guard let function = body.firstMatch(of: /<function=([^>\n]+)>/) else { return nil }
        var args = [String: Any]()
        for m in body.matches(of: /<parameter=([^>\n]+)>\n?(.*?)\n?<\/parameter>/.dotMatchesNewlines()) {
            let raw = String(m.2)
            // Values are written as plain text; keep numbers, booleans and
            // JSON objects typed when they parse as JSON.
            if let data = raw.data(using: .utf8),
               let value = try? JSONSerialization.jsonObject(with: data, options: [.fragmentsAllowed]),
               !(value is String) {
                args[String(m.1)] = value
            } else {
                args[String(m.1)] = raw
            }
        }
        let encoded = (try? JSONSerialization.data(withJSONObject: args, options: [.sortedKeys])) ?? Data("{}".utf8)
        return ToolCall(name: String(function.1), arguments: String(decoding: encoded, as: UTF8.self))
    }
}

Parameter values in the XML format are plain text, so the parser keeps numbers, booleans and objects typed when they parse as JSON (3 becomes 3, not "3"). The output is the OpenAI shape, with arguments as a JSON string. Going the other way, clients send earlier tool calls back with string arguments, and the template wants objects, so the route converts them:

code/Sources/serve/OpenAI.swiftswift
/// OpenAI clients send `arguments` as a JSON string; chat templates want an object.
func templateMessage(_ raw: [String: Any]) -> [String: any Sendable] {
    var message = raw
    if let calls = raw["tool_calls"] as? [[String: Any]] {
        message["tool_calls"] = calls.map { call -> [String: Any] in
            var call = call
            if var function = call["function"] as? [String: Any],
               let args = function["arguments"] as? String,
               let data = args.data(using: .utf8),
               let object = try? JSONSerialization.jsonObject(with: data) {
                function["arguments"] = object
                call["function"] = function
            }
            return call
        }
    }
    if message["content"] is NSNull { message["content"] = "" }
    return message.mapValues(sendableJSON)
}

The unit tests cover both formats, and a full round trip against Qwen3.5-0.8B works: asked for the weather in Oslo, the model calls get_weather({"city":"Oslo"}), receives {"temp_c": -3, "sky": "snow"}, and answers "The weather in Oslo is currently cold and snowy, with a temperature of -3°C."

Streaming tool calls

Streaming makes tool calls harder: the client must not receive <tool_call><function=get_wea as content. The route in Lesson 12 handles this when the request includes tools. As soon as streamed text contains a <, it starts buffering. If the buffer turns out not to be the start of <tool_call>, it is released as ordinary content. If it is, buffering continues to the end, and the parsed calls go out as one tool_calls delta with finish_reason: "tool_calls":

data: {"choices":[{"index":0,"delta":{"tool_calls":[{"index":0,"id":"call_28389224","type":"function",
       "function":{"name":"get_weather","arguments":"{\"city\":\"Paris\"}"}}]}}]}
data: {"choices":[{"index":0,"delta":{},"finish_reason":"tool_calls"}]}

OpenAI streams call arguments in fragments; sending a complete call in one delta is also valid, and every client accepts it.

Metrics

The questions an operator asks are: is it up, how loaded is it, are clients being turned away, how long do they wait for the first token, and is the prompt cache working. A few counters answer them, exposed at /metrics in Prometheus' text format:

code/Sources/serve/Metrics.swiftswift
/// Counters exposed at /metrics in the Prometheus text format.
final class Metrics: Sendable {
    struct Values {
        var requests = 0
        var rejected = 0
        var cancelled = 0
        var promptTokens = 0
        var cachedPromptTokens = 0
        var completionTokens = 0
        var timeToFirstTokenSum = 0.0
        var timeToFirstTokenCount = 0
        var decodeSecondsSum = 0.0
        var inFlight = 0
    }

    private let values = OSAllocatedUnfairLock(initialState: Values())

    func update(_ body: @Sendable (inout Values) -> Void) {
        values.withLock { body(&$0) }
    }

    func render() -> String {
        let v = values.withLock { $0 }
        return """
            # TYPE qwenserve_requests_total counter
            qwenserve_requests_total \(v.requests)
            # TYPE qwenserve_rejected_total counter
            qwenserve_rejected_total \(v.rejected)
            # TYPE qwenserve_cancelled_total counter
            qwenserve_cancelled_total \(v.cancelled)
            # TYPE qwenserve_prompt_tokens_total counter
            qwenserve_prompt_tokens_total \(v.promptTokens)
            # TYPE qwenserve_cached_prompt_tokens_total counter
            qwenserve_cached_prompt_tokens_total \(v.cachedPromptTokens)
            # TYPE qwenserve_completion_tokens_total counter
            qwenserve_completion_tokens_total \(v.completionTokens)
            # TYPE qwenserve_time_to_first_token_seconds summary
            qwenserve_time_to_first_token_seconds_sum \(v.timeToFirstTokenSum)
            qwenserve_time_to_first_token_seconds_count \(v.timeToFirstTokenCount)
            # TYPE qwenserve_decode_seconds_total counter
            qwenserve_decode_seconds_total \(v.decodeSecondsSum)
            # TYPE qwenserve_in_flight gauge
            qwenserve_in_flight \(v.inFlight)

            """
    }
}

The route records them by wrapping each request's event stream, so neither the engines nor the HTTP code needed changing:

code/Sources/serve/main.swiftswift
/// Wraps an event stream to record request metrics as events pass through.
func instrument(_ events: AsyncThrowingStream<GenerationEvent, Error>) -> AsyncThrowingStream<GenerationEvent, Error> {
    metrics.update { $0.requests += 1; $0.inFlight += 1 }
    let start = Date()
    return AsyncThrowingStream { continuation in
        let task = Task {
            var first: Date?
            var finished = false
            do {
                for try await event in events {
                    if first == nil, case .text = event {
                        first = Date()
                        let ttft = first!.timeIntervalSince(start)
                        metrics.update { $0.timeToFirstTokenSum += ttft; $0.timeToFirstTokenCount += 1 }
                    }
                    if case .finished(let reason, let usage) = event {
                        finished = true
                        let decode = first.map { Date().timeIntervalSince($0) } ?? 0
                        metrics.update {
                            $0.promptTokens += usage.promptTokens
                            $0.cachedPromptTokens += usage.cachedTokens
                            $0.completionTokens += usage.completionTokens
                            $0.decodeSecondsSum += decode
                            if reason == .cancelled { $0.cancelled += 1 }
                        }
                    }
                    continuation.yield(event)
                }
                continuation.finish()
            } catch {
                continuation.finish(throwing: error)
            }
            // A client that disconnects never sees the finished event.
            let sawFinish = finished
            metrics.update {
                $0.inFlight -= 1
                if !sawFinish { $0.cancelled += 1 }
            }
        }
        continuation.onTermination = { _ in task.cancel() }
    }
}

Average time to first token is sum / count; decode speed is completion tokens divided by decode seconds; the cache hit rate is cached prompt tokens over prompt tokens. A disconnected client never sees its .finished event, so the wrapper counts a stream that ends without one as cancelled.

Running as a service

Build in Release, copy the binary somewhere stable, and let launchd start it at login and restart it if it exits:

<?xml version="1.0" encoding="UTF-8"?>
<!-- ~/Library/LaunchAgents/local.qwenserve.plist -->
<!DOCTYPE plist PUBLIC "-//Apple//DTD PLIST 1.0//EN" "http://www.apple.com/DTDs/PropertyList-1.0.dtd">
<plist version="1.0">
<dict>
  <key>Label</key><string>local.qwenserve</string>
  <key>ProgramArguments</key>

    <string>/usr/local/bin/serve</string>

    <string>--bits</string><string>8</string>
    <string>--port</string><string>8080</string>

  <key>KeepAlive</key><true/>

  <key>StandardErrorPath</key><string>/tmp/qwenserve.log</string>
</dict>
</plist>
launchctl bootstrap gui/$(id -u) ~/Library/LaunchAgents/local.qwenserve.plist
curl -s localhost:8080/health        # ok
launchctl bootout gui/$(id -u)/local.qwenserve   # stop it

The MLX Metal library is a bundle next to the binary (mlx-swift_Cmlx.bundle); copy it along with the executable, or the server fails the first time it touches the GPU.

What is still missing

The server is complete for one person or a small trusted group on one machine. Before exposing it more widely, add:

  • Authentication and TLS. Put it behind a reverse proxy that checks API keys and terminates TLS, and keep it bound to localhost.
  • A memory budget. Limit total cache memory across running requests and prompt-cache entries, and reject or queue requests whose context would exceed it, instead of discovering the limit by running out of memory.
  • Structured output. JSON-schema-constrained generation works by masking, at every step, the logits of tokens that would make the output invalid. The sampler from Lesson 10 is the place to add the mask; the hard part is a grammar engine that computes the allowed tokens quickly.
  • Reasoning content. With thinking enabled, separate the <think> block into its own field (several clients expect reasoning_content) rather than mixing it into the answer.
  • Several models, loaded on demand and evicted under memory pressure, with the model chosen by the request's model field.

You now have every piece: model code you can prove correct, caches for two kinds of attention, a scheduler for one GPU and many clients, two ways to make decode faster, and a method for measuring what each change is worth on the hardware in front of you.

Lesson in one breath

Tools go into the chat template; the model answers with <tool_call> blocks, JSON in Qwen3 and XML-like tags in Qwen3.5, which the parser turns into OpenAI tool_calls. While streaming, text is buffered from the first possible '<tool_call>' so markup never reaches the client. Counters for requests, rejections, cancellations, tokens and time to first token answer most operational questions. launchd keeps the server running. Authentication, a memory budget and structured output are the next steps.

Exercise 1one answer

Why does the streaming route buffer text once a '<' appears in a request that has tools?

If the buffer proves not to be a tool call, it is released as content; otherwise the calls are parsed and sent at the end.

A Qwen3.5 parameter value is written as 3 inside a <parameter=days> block. What does the parser put in the arguments JSON?

Values that parse as JSON numbers, booleans or objects keep their type; other text stays a string.
