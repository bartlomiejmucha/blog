20. Performance engineering

Measure before optimizing, and measure correctly. Collect every performance lesson from building this server into one method: what to time, how to keep the numbers honest, and which changes actually moved them.

By the end of this lesson you can

  • Benchmark inference code without fooling yourself
  • Break a decode step into components and time each one
  • Know which optimizations paid off in this server, and by how much
  • Keep memory use under control on a small machine

Keep the numbers honest

Every misleading number met while building this course came from one of these:

  • Debug builds. 36 vs 89 tokens per second for the same decode. Debug inflates CPU overhead, which changes not just absolute numbers but conclusions: MTP looked like a 1.4× win in Debug and was a slowdown at 4 bits in Release.
  • Laziness. Timing code that builds a graph without evaluating it measures nothing. Every timed region must end in eval or item.
  • Warm-up. The first call to a kernel includes compiling and caching it. The 4096×4096 matmul in Lesson 3 took 298 ms cold and 94 ms warm.
  • Noise. The M1 in a fanless laptop throttles when hot; repeated runs varied by about ±10%. Once, a run reversed a result entirely, while the disk was nearly full and the system was paging. Repeat measurements, alternate the variants you compare, and look at all runs, not the best one.

Time the parts

End-to-end tokens per second tells you that something is slow, not what. The infer tool's bench mode times the components of a speculative step separately:

The pipelining measurement, repeated five times in alternation, was the most stable result in the course: 10.8 to 11.0 ms per token with pipelining, 12.1 to 12.2 without.

if mode == "perf" {
    // 1. Decode with and without queueing the next step before reading the current token.
    let p = Array(prompt.prefix(16))
    for pipelined in [true, false] {
        let caches = model.makeCaches()
        _ = model(MLXArray(p.map(Int32.init)).reshaped(1, -1), caches: caches)
        var token = MLXArray([Int32(1)]).reshaped(1, 1)
        let n = 100
        let t0 = Date()
        if pipelined {
            var next = argMax(model(token, caches: caches)[0..., -1, 0...], axis: -1).reshaped(1, 1)
            asyncEval(next)
            for _ in 0 ..< n {
                let current = next
                next = argMax(model(current, caches: caches)[0..., -1, 0...], axis: -1).reshaped(1, 1)
                asyncEval(next)
                _ = current.item(Int.self)
            }
        } else {
            for _ in 0 ..< n {
                token = argMax(model(token, caches: caches)[0..., -1, 0...], axis: -1).reshaped(1, 1)
                _ = token.item(Int.self)
            }
        }
        print("decode pipelined=\(pipelined): \(String(format: "%.2f", Date().timeIntervalSince(t0) / Double(n) * 1000)) ms/token")

Memory

On an 8 GB machine, memory is as much a constraint as speed. The numbers to know:

  • Loading peaks above steady state. Quantizing on load reads the bfloat16 weights first: Qwen3.5-0.8B peaks at about 2 GB and settles at about 0.5 GB. A pre-quantized checkpoint avoids the peak but, for Qwen3.5, loses the MTP head.
  • MLX keeps freed buffers. For speed, MLX caches GPU buffers it has freed rather than returning them to the system. The engine calls MLX.Memory.clearCache() after each request so a long prompt's temporary buffers do not stay allocated forever. MLX.Memory.activeMemory and peakMemory report usage; log them during load tests.
  • Caches dominate at long context. Lesson 9's calculator. The prompt cache multiplies it: four stored long conversations can outweigh the model.

For a deeper view, Xcode's Instruments has a Metal System Trace template that shows every kernel on the GPU timeline, which is how you would find, for example, gaps where the GPU waits for the CPU.

Lesson in one breath

Measure Release builds, warm up, synchronize with eval, repeat, and watch for thermal and system noise. Time components in isolation: the 1-token and 2-token passes, the output projection, the drafter, single kernels at different row counts. In this server the big wins were Release over Debug (2.5×), the custom linear-attention kernel (3× prefill), CPU/GPU pipelining (11%), removing GPU synchronizations, and choosing weight precision to suit the kernels.
