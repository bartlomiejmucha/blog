12. Streaming and cancellation

Send each piece of text the moment it exists with server-sent events, and stop generating the instant a client goes away so the GPU is never wasted on nobody.

By the end of this lesson you can

  • Write a server-sent event stream in the Chat Completions chunk format
  • Connect the engine's AsyncThrowingStream to the HTTP response body
  • Propagate a client disconnect back to the worker as cancellation
  • Explain why cancellation is a throughput feature, not a nicety

Server-sent events

Streaming in the OpenAI API uses server-sent events (SSE), the simplest streaming format on the web: a long-lived HTTP response with content type text/event-stream, made of lines starting with data: , each event followed by a blank line.

data: {"id":"chatcmpl-1","object":"chat.completion.chunk","choices":[{"index":0,"delta":{"role":"assistant"}}]}

data: {"id":"chatcmpl-1","object":"chat.completion.chunk","choices":[{"index":0,"delta":{"content":"Here"}}]}

data: {"id":"chatcmpl-1","object":"chat.completion.chunk","choices":[{"index":0,"delta":{"content":" is"}}]}

data: {"id":"chatcmpl-1","object":"chat.completion.chunk","choices":[{"index":0,"delta":{},"finish_reason":"stop"}],"usage":{...}}

data: [DONE]

The first chunk carries the role, each following chunk a delta with new content, the last one the finish reason (and, in this server, the token usage), and [DONE] closes the stream. Clients concatenate the deltas.

struct ChatChunk: Encodable {

        var index = 0
        var delta: Delta
        var finishReason: String?
    }
    var id: String
    var object = "chat.completion.chunk"
    var created: Int
    var model: String
    var choices: [Choice]
    var usage: UsageBody?
}

Writing the stream

        status: .ok,
        headers: [.contentType: "text/event-stream", .cacheControl: "no-cache"],

            func send(_ chunk: ChatChunk) async throws {
                let data = try jsonEncoder.encode(chunk)
                try await writer.write(ByteBuffer(string: "data: " + String(decoding: data, as: UTF8.self) + "\n\n"))
            }
            try await send(ChatChunk(id: id, created: created, model: modelName,

            // Text streams through until a tool call starts. From there it
            // is buffered and sent as one structured delta at the end.
            var buffered = ""
            // If the client disconnects, the write throws, this loop ends,
            // and the stream's onTermination cancels the job in the engine.
            for try await event in events {
                switch event {
                case .text(let text):

                        buffered += text
                        // Release text once it is clearly not the start of a call.
                        if !buffered.contains(ToolCallParser.openTag)
                            && !ToolCallParser.openTag.hasPrefix(buffered.suffix(from: buffered.lastIndex(of: "<") ?? buffered.startIndex)) {
                            try await send(ChatChunk(id: id, created: created, model: modelName,
                                                     choices: [.init(delta: .init(content: buffered))]))
                            buffered = ""
                        }
                    } else {
                        try await send(ChatChunk(id: id, created: created, model: modelName,
                                                 choices: [.init(delta: .init(content: text))]))
                    }
                case .finished(let reason, let usage):
                    let (content, calls) = ToolCallParser.parse(buffered)
                    if !calls.isEmpty {
                        try await send(ChatChunk(id: id, created: created, model: modelName,
                                                 choices: [.init(delta: .init(content: content.isEmpty ? nil : content,
                                                                              toolCalls: toolCallBodies(calls)))]))
                    } else if !buffered.isEmpty {
                        try await send(ChatChunk(id: id, created: created, model: modelName,
                                                 choices: [.init(delta: .init(content: buffered))]))
                    }
                    try await send(ChatChunk(id: id, created: created, model: modelName,
                                             choices: [.init(delta: .init(),
                                                             finishReason: calls.isEmpty ? reason.rawValue : "tool_calls")],
                                             usage: usageBody(usage)))
                }
            }
            try await writer.write(ByteBuffer(string: "data: [DONE]\n\n"))
            try await writer.finish(nil)
        })

ResponseBody { writer in ... } hands the route a writer for the response body. Hummingbird sends the headers right away and keeps the connection open while the closure runs. Inside, the route iterates the engine's event stream with for try await and writes one SSE chunk per event. Each write goes out to the socket as soon as it is called, so the client sees each token within milliseconds of the worker producing it.

The buffered logic in the middle holds text back once it might be the start of a tool call, so tool calls go out as one structured chunk. Lesson 21 explains it; without tools, every text event goes straight through.

The bridge: AsyncThrowingStream

The worker is an ordinary thread producing tokens in a loop. The HTTP route is async Swift code. AsyncThrowingStream connects them:

code/Sources/Inference/Engine.swiftswift
/// Queues a request. Throws `queueFull` instead of letting the backlog
/// grow without bound, so the HTTP layer can answer 429 right away.
public func submit(_ request: GenerationRequest) throws -> AsyncThrowingStream<GenerationEvent, Error> {
    let (stream, continuation) = AsyncThrowingStream.makeStream(of: GenerationEvent.self, throwing: Error.self)
    let job = Job(request: request, continuation: continuation)
    // Fires when the consumer stops listening, e.g. the client disconnects.
    continuation.onTermination = { _ in job.cancel() }
    try inbox.withLock { queue in
        guard queue.count < maxQueue else { throw EngineError.queueFull }
        queue.append(job)
    }
    wake.signal()
    return stream
}

makeStream returns the stream, which the route consumes, and its continuation, which the worker keeps. The worker calls continuation.yield(.text(...)) for each piece and finish() at the end; these calls are thread-safe, so the worker thread never has to touch Swift concurrency. Events are buffered until the consumer reads them, so a slow client does not slow the worker.

Cancellation

The most important line in submit is this one:

continuation.onTermination = { _ in job.cancel() }

Follow what happens when a user closes the browser tab halfway through a long answer:

  1. The next writer.write in the route throws, because the socket is gone.
  2. The error ends the for try await loop, and the stream's consumer goes away.
  3. The stream terminates and calls onTermination, which sets the job's cancelled flag.
  4. The worker checks the flag after every token and stops:
code/Sources/Inference/Engine.swiftswift
/// A request waiting for, or being served by, the worker.
final class Job: Sendable {
    let request: GenerationRequest
    let continuation: AsyncThrowingStream<GenerationEvent, Error>.Continuation
    private let cancelledFlag = OSAllocatedUnfairLock(initialState: false)

    init(request: GenerationRequest, continuation: AsyncThrowingStream<GenerationEvent, Error>.Continuation) {
        self.request = request
        self.continuation = continuation
    }

    var cancelled: Bool { cancelledFlag.withLock { $0 } }
    func cancel() { cancelledFlag.withLock { $0 = true } }
}

The flag is behind an OSAllocatedUnfairLock, so setting it from an HTTP thread and reading it from the worker is safe. Checking once per token costs nothing measurable.

Why this matters: without it, an abandoned 2,000-token request keeps the GPU busy for half a minute, and every queued request waits behind it. In the finished server, a request sent one second after a client disconnected mid-stream from such a request was answered in 0.2 seconds. Cancellation is a throughput feature.

Lesson in one breath

A streamed response is a sequence of 'data: {json}' lines separated by blank lines, ending with 'data: [DONE]'. Hummingbird's ResponseBody gives the route a writer; the route loops over the engine's event stream and writes one chunk per text piece. When the client disconnects, the write throws, the loop ends, the stream terminates, and its onTermination handler flips the job's cancelled flag, which the worker checks after every token.

Exercise 1one answer

How does an SSE client know where one event ends?

SSE is line-based: one or more data: lines, then an empty line.

Exercise 2put in order

A client disconnects mid-stream. Order what happens next.

The route's next write throws
The for-await loop over events ends
The stream terminates and calls onTermination
The job's cancelled flag is set
The worker sees the flag after the current token and stops

The disconnect is noticed on the next write; termination of the stream is the hand-off point between HTTP and the engine.

Exercise 3one answer

Why can the worker thread call continuation.yield without being part of Swift concurrency?

AsyncStream continuations are designed to be fed from any thread, which makes them the standard bridge from callback or thread-based code to async code.

Exercise 4one answer

Without cancellation, what is the main cost of a client that disconnects early?

The single GPU worker is the scarcest resource. Wasting it delays everyone else.
