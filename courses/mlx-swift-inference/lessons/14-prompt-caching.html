14. Prompt caching

The second turn of a chat repeats the whole first turn. Keep the caches of recent requests and skip prefilling what the server has already seen, and learn why where you take the snapshot matters as much as how you match it.

By the end of this lesson you can

  • Explain when cached state from one request can be reused by another
  • Copy caches safely so stored entries are never mutated
  • Find why naive end-of-reply caching misses for Qwen3.5, and fix it
  • Measure the effect on time to first token

The opportunity

A chat client sends the whole conversation every time. Turn 3 of a conversation with a long system prompt contains the system prompt, turn 1, the reply to it, turn 2, the reply to that, and the new message. Without caching, the server prefills all of it again, and time to first token grows with every turn.

But the caches after prefilling a prompt depend only on its tokens. If the server kept the caches from turn 2, turn 3 would only need to prefill what is new. The same works for many requests that share a long system prompt.

Storing and finding entries

code/Sources/Inference/PromptCache.swiftswift
/// Keeps the caches of recent requests so a follow-up that starts with the
/// same tokens (the next turn of a chat, a shared system prompt) skips
/// prefilling them.
///
/// Matching is on whole entries: an entry is used only if all of its
/// tokens are a prefix of the new prompt. Attention caches could be trimmed
/// to a shorter common prefix, but linear-attention state cannot, so this
/// rule works for both kinds of layer.
///
/// What to store matters as much as how to match. Chat templates often
/// re-render earlier turns differently from how they were generated (Qwen3.5
/// drops the empty think block from past answers), so the state at the end
/// of a reply rarely matches the next prompt. The engine instead stores the
/// state at the start of the last `<|im_start|>` in the prompt: everything
/// before it is history that the next turn repeats verbatim.
final class PromptCache {
    struct Entry {
        var tokens: [Int]
        var caches: [LayerCache]
    }

    let capacity: Int
    private var entries: [Entry] = []   // most recently used last

    init(capacity: Int) {
        self.capacity = capacity
    }

    /// Returns caches to start from and how many prompt tokens they cover.
    /// At least one prompt token is always left to run, because generation
    /// needs the logits of the last prompt position.
    func lookup(prompt: [Int], model: any LanguageModel) -> (caches: [LayerCache], count: Int) {
        let best = entries.indices
            .filter { entries[$0].tokens.count < prompt.count && prompt.starts(with: entries[$0].tokens) }
            .max { entries[$0].tokens.count < entries[$1].tokens.count }
        guard let index = best, capacity > 0 else { return (model.makeCaches(), 0) }

        let entry = entries.remove(at: index)
        entries.append(entry)
        return (entry.caches.map { $0.copy() }, entry.tokens.count)
    }

    func store(tokens: [Int], caches: [LayerCache]) {
        guard capacity > 0, caches.first?.offset == tokens.count else { return }
        // A new entry supersedes any entry it extends.
        entries.removeAll { tokens.starts(with: $0.tokens) }
        entries.append(Entry(tokens: tokens, caches: caches))
        if entries.count > capacity { entries.removeFirst() }
    }
}

Each entry is a token list and the caches that hold exactly those tokens. lookup picks the longest entry whose tokens are a prefix of the new prompt and leaves at least one prompt token to run, because generation needs the logits of the last prompt position. store drops entries that the new one extends and evicts the least recently used entry beyond a fixed capacity (4 by default). A production server would budget by bytes instead of by count, since entries for long prompts can be hundreds of megabytes.

Why whole entries only? With attention caches you could reuse a partial match by trimming the cache back to the common prefix. Qwen3.5's linear-attention layers keep a running state that cannot be rewound to an arbitrary earlier position (Lesson 17). Requiring the whole entry to match works for both kinds of layer.

Copies, not references

code/Sources/Inference/PromptCache.swiftswift
extension KVCache {
    /// An independent copy. `update` writes into the key and value buffers
    /// in place, so a stored cache must never be handed out directly.
    public func copy() -> LayerCache {
        let c = KVCache()
        if let keys, let values {
            c.keys = keys[.ellipsis, ..<offset, 0...]
            c.values = values[.ellipsis, ..<offset, 0...]
        }
        c.offset = offset
        return c
    }
}

The KV cache from Lesson 9 writes new keys into its buffer in place. Hand a stored entry's cache to a new request, and that request's generated tokens overwrite the stored state: the next request that matches the entry gets corrupted keys. So lookup returns copies. Slicing out the filled part creates new arrays, and the next update allocates a fresh buffer.

The linear-attention cache needs no deep copy, because its update replaces the state arrays instead of writing into them. Sharing references to arrays nobody mutates is safe. The difference is one of those details that only shows up as a rare, baffling bug if you get it wrong.

The first attempt missed

The obvious design stores the caches after each request finishes, covering the prompt and the generated reply, so that the next turn, which starts with exactly that conversation, hits. Implemented that way and tested with a three-turn Qwen3.5 conversation, it hit zero times.

The reason is in the chat template. Render the same conversation before and after a turn:

turn 1 prompt:   ...<|im_start|>user\nWhat is MLX?<|im_end|>\n<|im_start|>assistant\n<think>\n\n</think>\n\n
turn 2 prompt:   ...<|im_start|>user\nWhat is MLX?<|im_end|>\n<|im_start|>assistant\nAn array framework.<|im_end|>\n<|im_start|>user\n...

When generating, the prompt ends with an empty think block. When the same reply appears as history in the next turn, the template leaves the think block out. So the tokens the caches hold after turn 1 are not a prefix of turn 2's prompt, and they never will be. Templates that strip reasoning from past turns are common, and even without that, re-tokenizing a reply does not always reproduce the exact tokens that were generated.

Snapshot where history ends

The fix is to snapshot the caches at a point the next turn is guaranteed to repeat: the start of the last <|im_start|> in the prompt. Everything before it is earlier turns plus the newest user message, all rendered from history; everything after it is the generation prompt, which changes. The generator already supports this: it ends a prefill chunk exactly at the checkpoint and copies the caches there.

code/Sources/Inference/Generator.swiftswift
while rest.count > 1 {
    var size = Swift.min(prefillStep, rest.count - 1)
    // End a chunk exactly at the checkpoint so the caches can be copied there.
    if let checkpoint, rest.startIndex < checkpoint {
        size = Swift.min(size, checkpoint - rest.startIndex)
    }
    let chunk = rest.prefix(size)
    _ = model(MLXArray(chunk.map(Int32.init)).reshaped(1, -1), caches: self.caches)
    eval(self.caches.flatMap(\.state))
    rest = rest.dropFirst(chunk.count)
    if rest.startIndex == checkpoint {
        checkpointCaches = self.caches.map { $0.copy() }
    }
}

The engine picks the checkpoint, prefills from the best cache hit, and stores the snapshot afterwards:

code/Sources/Inference/Engine.swiftswift
// Reuse the caches of an earlier request whose tokens are a prefix
// of this prompt, and only prefill the rest.
let hit = promptCache.lookup(prompt: request.prompt, model: loaded.model)
cached = hit.count
checkpoint = request.prompt.lastIndex(of: loaded.turnStartToken ?? -1).flatMap {
    $0 > cached ? $0 : nil
}
plain = TokenGenerator(
    model: loaded.model, prompt: Array(request.prompt[cached...]),
    parameters: request.parameters, maxTokens: request.maxTokens, caches: hit.caches,
    checkpoint: checkpoint.map { $0 - cached })
code/Sources/Inference/Engine.swiftswift
if let checkpoint, let caches = plain?.checkpointCaches {
    promptCache.store(tokens: Array(request.prompt[..<checkpoint]), caches: caches)
}

With this change, the same three-turn conversation with a 1,500-token system prompt on Qwen3.5-0.8B:

turn 1: 3.25 s   prompt 1573 tokens, cached    0
turn 2: 0.97 s   prompt 1622 tokens, cached 1566
turn 3: 0.93 s   prompt 1669 tokens, cached 1615

Each later turn prefills only about 55 new tokens. The cached count appears in the response as usage.prompt_tokens_details.cached_tokens, so clients can see it too.

A limitation to know. The MTP generator of Lesson 19 keeps a second cache for its drafting head, which this prompt cache does not store. So the serial engine uses the prompt cache only when MTP is off (--no-mtp), and MTP requests prefill from scratch. That is a real trade-off: long multi-turn chats favour the prompt cache, short prompts with long answers favour MTP. Extending the cache entries to carry the drafter's cache is a good exercise once you have read Lesson 19.

Lesson in one breath

If an earlier request's tokens are a prefix of a new prompt, its caches already hold the state for that prefix, and only the rest needs prefilling. Store copies, because attention caches are written in place. Matching needs whole-entry prefixes, since linear-attention state cannot be trimmed. And store the snapshot at the last <|im_start|> of the prompt, not at the end of the reply: chat templates re-render past replies differently from how they were generated.

Exercise 1one answer

Why must lookup return copies of the stored caches?

Without copies, the first request to use an entry corrupts it for every later request.

Exercise 2one answer

Why does caching the state at the end of each reply never hit with Qwen3.5's template?

The next prompt differs from the stored tokens right where the reply starts. The fix is to snapshot at a point the template repeats verbatim.

Exercise 3compute it

An entry covers 1,566 tokens and the new prompt has 1,622. How many tokens must be prefilled?

1,622 − 1,566 = 56. The last of them produces the logits for the first generated token.

Exercise 4one answer

Why does the cache only match whole entries rather than the longest common prefix?

Attention caches can be trimmed; a running recurrent state cannot. Whole-entry matching works for both.
