9. The generation loop and the KV cache

Turn a model into a token stream: prefill the prompt in chunks, keep every past key and value in a cache that grows in steps, and overlap CPU and GPU work so the GPU never waits.

By the end of this lesson you can

  • Explain why caching keys and values turns decode from quadratic into linear work
  • Compute KV cache memory for a model and context length
  • Implement a cache that appends without copying the whole history every token
  • Write a generation loop with chunked prefill and pipelined decode

Prefill and decode

Lesson 1 named the two phases. Now look at what the model computes in each. Attention at position t needs the keys and values of every position up to t. Those depend only on earlier tokens, which never change. So instead of recomputing them for every new token, store them:

  • Prefill runs the model on the whole prompt at once. Each attention layer computes keys and values for all prompt positions and stores them in its cache. The logits at the last position give the first generated token.
  • Decode runs the model on one token. Each layer computes that token's key and value, appends them to the cache, and attends to the whole cache.

Without the cache, generating n tokens would cost work proportional to 1 + 2 + … + n, which grows as n². With it, each step does one token's worth of projections plus an attention read over the cache.

How big the cache gets

Per token, each attention layer stores one key and one value vector per KV head:

bytes per token = layers × 2 × kv_heads × head_dim × bytes per value

For Qwen3-0.6B in bfloat16: 28 × 2 × 8 × 128 × 2 = 114,688 bytes, about 112 KB per token. A 32,000-token context then needs 3.5 GB, roughly ten times the 4-bit weights. On long contexts the cache, not the model, decides how many requests fit in memory, and reading it is part of every decode step's memory traffic.

Qwen3.5 changes this picture dramatically. Only 6 of its 24 layers keep a KV cache, with 2 KV heads each; the other 18 keep a fixed-size state instead (Lesson 17). Try both models below.

A cache that grows in steps

code/Sources/Inference/KVCache.swiftswift
/// Keys and values for one attention layer, stored in a buffer that grows in
/// fixed steps so that decoding one token does not copy the whole history.
public final class KVCache {
    public internal(set) var offset = 0
    var keys: MLXArray?
    var values: MLXArray?
    let step = 256

    public init() {}

    /// Appends `[B, kvHeads, L, headDim]` keys and values and returns
    /// everything cached so far, including the new entries.
    public func update(keys newKeys: MLXArray, values newValues: MLXArray) -> (MLXArray, MLXArray) {
        let previous = offset
        let count = newKeys.dim(2)

        if keys == nil || previous + count > keys!.dim(2) {
            let (B, H, _, D) = (newKeys.dim(0), newKeys.dim(1), newKeys.dim(2), newKeys.dim(3))
            let capacity = ((count + step - 1) / step) * step
            let k = MLXArray.zeros([B, H, capacity, D], dtype: newKeys.dtype)
            let v = MLXArray.zeros([B, H, capacity, newValues.dim(3)], dtype: newValues.dtype)
            if let keys, let values {
                self.keys = concatenated([keys[.ellipsis, ..<previous, 0...], k], axis: 2)
                self.values = concatenated([values[.ellipsis, ..<previous, 0...], v], axis: 2)
            } else {
                self.keys = k
                self.values = v
            }
        }

        offset += count
        keys![.ellipsis, previous ..< offset, 0...] = newKeys
        values![.ellipsis, previous ..< offset, 0...] = newValues
        return (keys![.ellipsis, ..<offset, 0...], values![.ellipsis, ..<offset, 0...])
    }

    /// Drops the newest `count` entries. Speculative decoding uses this to
    /// discard rejected draft tokens.
    public func trim(_ count: Int) {
        offset -= min(count, offset)
    }

    /// The arrays that hold the cache, for `eval` and memory accounting.
    public var state: [MLXArray] { [keys, values].compactMap { $0 } }
}

The naive cache concatenates new keys onto old ones every step. That copies the whole history every token, which is quadratic again, just with a smaller constant. This cache allocates room for 256 positions at a time and writes each new token into the next free slot. Only when the buffer is full does it allocate the next block and copy. update returns a view of the filled part, which is what attention reads.

trim moves the write position back without touching memory. Speculative decoding (Lesson 19) uses it to forget draft tokens the model rejected, and it is why a cache that "forgets" can be nearly free.

The generator

code/Sources/Inference/Generator.swiftswift
/// Produces tokens one at a time for a single sequence.
///
/// The prompt is processed in chunks (prefill), then the loop feeds each
/// sampled token back in (decode). The next step is queued on the GPU before
/// the current token is handed to the caller, so the CPU work between steps
/// overlaps with GPU work.
public struct TokenGenerator: Sequence, IteratorProtocol {
    let model: any LanguageModel
    public let caches: [LayerCache]
    var sampler: Sampler
    var pending: MLXArray
    let maxTokens: Int
    public private(set) var generated = 0
    /// Every token that has been run through the model, in order. The
    /// caches hold exactly these positions.
    public private(set) var fed: [Int] = []
    /// Copies of the caches taken when prefill reached `checkpoint`.
    public private(set) var checkpointCaches: [LayerCache]?

    public init(
        model: any LanguageModel, prompt: [Int], parameters: SamplingParameters,
        maxTokens: Int, caches: [LayerCache]? = nil, prefillStep: Int = 512,
        checkpoint: Int? = nil
    ) {
        self.model = model
        self.caches = caches ?? model.makeCaches()
        self.sampler = Sampler(parameters)
        self.maxTokens = maxTokens

        // Prefill all but the last prompt token in chunks. Only the cache
        // matters here, the logits are thrown away.
        var rest = prompt[...]
        fed = prompt
        while rest.count > 1 {
            var size = Swift.min(prefillStep, rest.count - 1)
            // End a chunk exactly at the checkpoint so the caches can be copied there.
            if let checkpoint, rest.startIndex < checkpoint {
                size = Swift.min(size, checkpoint - rest.startIndex)
            }
            let chunk = rest.prefix(size)
            _ = model(MLXArray(chunk.map(Int32.init)).reshaped(1, -1), caches: self.caches)
            eval(self.caches.flatMap(\.state))
            rest = rest.dropFirst(chunk.count)
            if rest.startIndex == checkpoint {
                checkpointCaches = self.caches.map { $0.copy() }
            }
        }
        pending = MLXArray(rest.map(Int32.init)).reshaped(1, -1)
        pending = step(pending)
        asyncEval(pending)
    }

    mutating func step(_ input: MLXArray) -> MLXArray {
        let logits = model(input, caches: caches)
        return sampler(logits[0..., -1, 0...])
    }

    public mutating func next() -> Int? {
        guard generated < maxTokens else { return nil }
        let current = pending
        if generated + 1 < maxTokens {
            // Queue step n+1 before reading token n off the GPU.
            pending = step(current.reshaped(1, 1))
            asyncEval(pending)
        }
        generated += 1
        let token = current.item(Int.self)
        if generated < maxTokens { fed.append(token) }
        return token
    }
}

Read it in three parts.

Chunked prefill. The prompt, except its last token, is run in chunks of 512. Chunking bounds the memory of one forward pass, since attention scores for a chunk scale with chunk × cache length. Each chunk's caches are evaluated immediately so the lazy graph does not grow across chunks. The last prompt token goes through the regular step, because it is the one whose logits matter.

Pipelined decode. In next(), the generator builds and asyncEvals the forward pass for the next token before calling item() on the current one. While the caller detokenizes and streams the current token, the GPU is already computing the next. On the M1 this takes decode from 12.15 to 10.9 ms per token, an 11% gain for four lines of code.

Bookkeeping. fed records every token that has gone into the model, so it always says exactly which positions the caches hold, including the look-ahead token. checkpoint copies the caches at a chosen prompt position. Both exist for the prompt cache in Lesson 14; ignore them for now.

Running it

With the sampler from the next lesson, this is the core of the infer tool: format a prompt, iterate the generator, stop at an end token, and stream text through the detokenizer.

let model = try loadQwen3(from: directory)
let tokenizer = try await AutoTokenizer.from(modelFolder: directory)
let prompt = try tokenizer.applyChatTemplate(
    messages: [["role": "user", "content": "Why is the sky blue?"]], tools: nil,
    additionalContext: ["enable_thinking": false])

var detokenizer = StreamingDetokenizer(tokenizer: tokenizer)
for token in TokenGenerator(model: model, prompt: prompt, parameters: .init(), maxTokens: 200) {
    if token == 151645 { break }               // <|im_end|>
    print(detokenizer.append(token), terminator: "")
}

On a base M1 with Qwen3-0.6B at 4 bits this streams at about 60 tokens per second in a Debug build. Remember Lesson 3: measure in Release.

Lesson in one breath

Without a cache, every new token would recompute keys and values for the entire history. The KV cache stores them once per token per layer, at a cost of 2 × kv_heads × head_dim × bytes per layer per token. The generator prefills the prompt in chunks, then repeatedly runs one token, samples, and feeds the sample back, queueing step n+1 on the GPU before handing token n to the caller.

Exercise 3one answer

Why does the cache grow in blocks of 256 positions instead of concatenating each new token?

Writing into preallocated space costs one token's worth of work; reallocating happens once per 256 tokens.

Exercise 4one answer

Why is the last prompt token not part of the prefill chunks?

Prefill chunks only need to fill the cache, so their logits are thrown away. The last position's logits produce the first token.

Exercise 5one answer

What does the generator overlap by calling asyncEval on step n+1 before item() on step n?

Without it, the GPU idles while the CPU handles each token. With it, the next forward pass is already running.
