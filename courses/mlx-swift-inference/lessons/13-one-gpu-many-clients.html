13. One GPU, many clients

Many HTTP requests arrive at once, but the model must run on one thread at a time. Build the serial engine: a dedicated worker thread, a locked inbox, backpressure, and a clear rule for which objects each thread may touch.

By the end of this lesson you can

  • Explain why model work belongs on one dedicated thread
  • Hand work between threads with a locked queue and a semaphore
  • Reject excess load early with a bounded queue
  • Reason about Sendable in a server that wraps non-thread-safe libraries

Why one thread

Hummingbird serves each connection on Swift's cooperative thread pool, so dozens of requests can be in flight at once. It is tempting to run the model right there in the route. Three reasons not to:

  • The GPU does one thing at a time anyway. Two forward passes submitted together do not finish faster than one after the other; they just compete. Concurrency at the model level only helps when it is designed in, which is what batching (Lesson 15) does.
  • The model is not thread-safe. Caches are mutated in place, MLX modules are classes, and nothing guards them. Two threads in one forward pass corrupt state silently.
  • The cooperative pool must not block. It has about one thread per CPU core. A route that spends ten seconds generating holds one of them hostage, and a few long requests can stall every other async task in the process, including the HTTP server itself.

So model work goes to one thread the engine owns, created for that purpose and nothing else.

The serial engine

code/Sources/Inference/Engine.swiftswift
/// Runs one request at a time on a dedicated thread.
///
/// The GPU can only do one thing at a time anyway, and MLX models are not
/// thread-safe, so all model work happens on the worker thread. Callers on
/// any thread hand requests over through a locked inbox and receive tokens
/// through an `AsyncThrowingStream`.
public final class SerialEngine: @unchecked Sendable {
    // Touched only by the worker thread.
    private let loaded: LoadedModel
    private let promptCache: PromptCache
    private let useMTP: Bool

    // Shared between threads, always behind the lock or the semaphore.
    private let inbox = OSAllocatedUnfairLock<[Job]>(initialState: [])
    private let wake = DispatchSemaphore(value: 0)
    private let maxQueue: Int

    public init(loaded: LoadedModel, maxQueue: Int = 16, useMTP: Bool = true, promptCacheEntries: Int = 4) {
        self.loaded = loaded
        self.maxQueue = maxQueue
        self.useMTP = useMTP
        self.promptCache = PromptCache(capacity: promptCacheEntries)
        let thread = Thread { [self] in self.run() }
        thread.name = "inference-worker"
        thread.stackSize = 16 << 20
        thread.start()
    }

    /// Queues a request. Throws `queueFull` instead of letting the backlog
    /// grow without bound, so the HTTP layer can answer 429 right away.
    public func submit(_ request: GenerationRequest) throws -> AsyncThrowingStream<GenerationEvent, Error> {
        let (stream, continuation) = AsyncThrowingStream.makeStream(of: GenerationEvent.self, throwing: Error.self)
        let job = Job(request: request, continuation: continuation)
        // Fires when the consumer stops listening, e.g. the client disconnects.
        continuation.onTermination = { _ in job.cancel() }
        try inbox.withLock { queue in
            guard queue.count < maxQueue else { throw EngineError.queueFull }
            queue.append(job)
        }
        wake.signal()
        return stream
    }

The worker is a plain Thread with a 16 MB stack. Deep model graphs build deep call stacks, and the default secondary-thread stack of 512 KB is not enough. It runs run() forever:

code/Sources/Inference/Engine.swiftswift
private func run() {
    while true {
        wake.wait()
        guard let job = inbox.withLock({ $0.isEmpty ? nil : $0.removeFirst() }) else { continue }
        if job.cancelled {
            job.continuation.finish()
            continue
        }
        serve(job)
    }
}

The hand-off uses two primitives:

  • The inbox is an array behind an OSAllocatedUnfairLock. submit, running on an HTTP thread, appends under the lock; the worker removes the first job under the lock. The lock is held for microseconds, never across model work.
  • The semaphore lets the worker sleep without spinning. Each submit signals it once; each loop iteration waits once. If ten jobs arrive while the worker is busy, the count reaches ten, and the worker runs ten iterations without sleeping.

A job cancelled while it was still waiting is finished immediately without touching the model.

Backpressure

Without a limit, an overloaded server accepts every request and makes each one wait longer. Clients time out, retry, and make it worse. The inbox therefore has a maximum length (16 by default), and submit throws queueFull beyond it. The route turns that into HTTP 429 "server busy, retry later" at once.

A fast, honest no is better than a slow failure. Clients and load balancers know what to do with 429: back off, or try another server. The queueDepth property and the qwenserve_rejected_total metric let you see when it happens and size the limit.

Sendable, honestly

Swift 6 checks at compile time that values shared between threads are safe to share (Sendable). MLX arrays and modules are not, and the engine holds them, so the compiler cannot prove the engine safe. The options:

  1. Make the engine an actor. Actor methods run on the cooperative pool, which brings back the blocking problem above, unless you give the actor a custom executor.
  2. Mark the engine @unchecked Sendable and enforce a rule by design.

The engine takes option 2, and the rule is written in the code: the model, the prompt cache and the generators are touched only by the worker thread; everything shared (the inbox, the semaphore, each job's cancelled flag) is protected by a lock or is itself thread-safe. @unchecked is not a way to silence the compiler; it moves the proof from the compiler to you, so the proof has to be short enough to check by reading.

The same reasoning gives PromptFormatter, which renders chat templates on HTTP threads. The tokenizer is not documented as thread-safe, so every call goes through a lock:

code/Sources/Inference/LoadedModel.swiftswift
/// Renders chat prompts from request handlers on any thread. The tokenizer
/// is not documented as thread-safe, so calls go through a lock.
public final class PromptFormatter: @unchecked Sendable {
    private let loaded: LoadedModel
    private let lock = NSLock()

    public init(_ loaded: LoadedModel) {
        self.loaded = loaded
    }

    public func render(
        messages: [[String: any Sendable]], tools: [[String: any Sendable]]?, enableThinking: Bool
    ) throws -> [Int] {
        try lock.withLock { try loaded.prompt(messages: messages, tools: tools, enableThinking: enableThinking) }
    }
}

Rendering takes well under a millisecond, so the lock never becomes a bottleneck, and the worker never renders templates, so it never waits on HTTP threads.

One request at a time

This engine serves requests strictly one after another. While one request decodes, the others wait in the inbox. For a personal server that is often exactly right: each request gets the full speed of the machine, and speculative decoding (Lesson 19) makes that speed higher still.

Under load it is wasteful. Lesson 2 showed that a decode step is limited by reading the weights, so a step that served eight sequences would cost little more than one serving a single sequence. Before exploiting that, the next lesson removes work entirely by not prefilling the same prompt twice.

Lesson in one breath

All MLX work happens on one dedicated worker thread, because the GPU serializes the work anyway and the model objects are not thread-safe. Requests cross from HTTP threads to the worker through an inbox protected by a lock, with a semaphore to wake the worker. The inbox is bounded, so overload becomes a fast 429 instead of an ever-growing wait. Objects only the worker touches are marked @unchecked Sendable with that rule written next to them.
