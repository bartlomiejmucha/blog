1. What an inference server does

Before writing code, see the whole machine: what happens between an HTTP request arriving and the last token leaving, and which part of the code owns each step.

The job

A language model is a function: give it a list of token ids, and it returns a score for every possible next token. That is all the model does. Everything else a product like ChatGPT does around it, from accepting messages over HTTP to streaming words back, is the job of an inference server.

In this course you build one from scratch, in Swift, on Apple's MLX framework. By the end it will:

  • load Qwen3 and Qwen3.5 checkpoints straight from Hugging Face, dense and mixture-of-experts, quantizing them on the fly;
  • run them with model code you wrote yourself, checked against the Python reference implementation;
  • speak the OpenAI Chat Completions API, including streaming and tool calls, so existing clients work unchanged;
  • serve many clients from one GPU, with a request queue, cancellation, prompt caching and continuous batching;
  • decode faster with speculative decoding, using the multi-token-prediction (MTP) head that ships inside every Qwen3.5 checkpoint.

This lesson is the map. Each stage you see here gets one or more lessons of its own later.

The life of a request

Follow one request through the finished server. A client sends:

curl localhost:8080/v1/chat/completions -H 'content-type: application/json' -d '{
  "messages": [{"role": "user", "content": "Why is the sky blue?"}],
  "stream": true
}'

The list says what each stage does and where its code lives; the diagram after it lets you step through them in order.

  1. HTTP layer (Sources/serve). Hummingbird parses the JSON body. Nothing here touches the model.
  2. Chat template. The messages are rendered into one string with the model's own template, for example <|im_start|>user\nWhy is the sky blue?<|im_end|>\n<|im_start|>assistant\n, and tokenized into integers.
  3. Queue. The token list goes into the engine's inbox. If the inbox is full, the client gets HTTP 429 right away instead of waiting forever.
  4. Prefill. A dedicated worker thread runs the model over the whole prompt in one pass. This fills the caches and produces the first token.
  5. Decode loop. The worker feeds each new token back in, one forward pass per token, until an end-of-turn token or the length limit.
  6. Detokenize and stream. Token ids become text, and each piece is sent to the client as a server-sent event while the next token is being computed.

Two numbers: time to first token and decode speed

Users judge a chat server by two things, and they come from different parts of the pipeline.

Time to first token (TTFT) is the wait before any text appears. It is dominated by prefill: the model must read the whole prompt before it can say anything. A long system prompt or a long chat history makes it worse. Prompt caching (Lesson 14) attacks it by skipping prompt tokens the server has already processed.

Decode speed, in tokens per second, is how fast text streams once it starts. Each new token costs one full forward pass, and as Lesson 2 shows, that pass is limited by how fast the chip can read the weights from memory, not by arithmetic. Quantization (Lesson 5), speculative decoding (Lessons 18 and 19) and batching (Lesson 15) all attack it from different angles.

A server also has a third number its operator cares about: throughput, the total tokens per second across all clients. Batching raises throughput, sometimes at the cost of each client's own decode speed. Keep the three apart; most performance discussions go wrong by mixing them up.

Concrete numbers from the finished server on a base M1 with 8 GB: Qwen3.5-0.8B with 4-bit weights decodes at about 90 tokens per second, and a 1,570-token prompt takes about 3.2 seconds to answer the first time and under 1 second on the next turn, when the prompt cache hits.

Run the finished server

You need a Mac with Apple Silicon, Xcode, and Python only for the download tool. Fetch a model and build the server:

# 1. A model. The original checkpoint, because it still contains the MTP head.
pip install -U huggingface_hub
hf download Qwen/Qwen3.5-0.8B --local-dir models/Qwen3.5-0.8B

# 2. Build in Release. xcodebuild, not "swift build": only Xcode's build
#    system compiles MLX's Metal shaders (Lesson 3).
cd code
xcodebuild build -scheme serve -configuration Release \
  -destination 'platform=OS X' -derivedDataPath DerivedData

# 3. Run it. --bits 8 quantizes to 8-bit on load; Lesson 19 explains why
#    8-bit is the sweet spot for speculative decoding on an M1.
DerivedData/Build/Products/Release/serve ../models/Qwen3.5-0.8B --bits 8 --port 8080

In another terminal:

curl -s localhost:8080/v1/chat/completions -H 'content-type: application/json' \
  -d '{"messages":[{"role":"user","content":"Name three planets."}],"temperature":0}'
# {"choices":[{"message":{"role":"assistant","content":"Earth, Mars, and Jupiter."},
#   "finish_reason":"stop",...}],"usage":{"prompt_tokens":19,"completion_tokens":7,...}}

Any OpenAI-compatible client works too: point its base URL at http://localhost:8080/v1. Now you know what you are building. The next lesson explains the single most important fact about running it fast.

Lesson in one breath

An inference server turns chat messages into tokens, runs the model once over the prompt (prefill) and then once per new token (decode), and streams text back as it goes. The hard parts are not the HTTP: they are keeping one GPU busy for many clients, reusing work between requests, and making each decode step cheap.

Exercise 1put in order

Put the stages of a streamed chat request in order.

Render messages with the chat template and tokenize
Put the request in the engine's inbox
Prefill: run the model over the whole prompt
Decode: one forward pass per new token
Detokenize each token and send it as a server-sent event

Template and tokenize first, because the engine only deals in token ids. The queue sits between the HTTP layer and the single worker. Prefill produces the first token; decode produces the rest; detokenizing and streaming happen as each token appears.

Exercise 2one answer

A user complains that answers take five seconds to start appearing, though they stream quickly afterwards. Which stage is the first suspect?

The wait before the first token is time to first token, and it is dominated by prefill: the model must process the whole prompt first. Long system prompts and chat histories make it worse. Fast streaming afterwards means decode is fine.

Exercise 3select all that apply

Which of these raise throughput (total tokens per second across all clients)? Select all that apply.

Batching amortizes each weight read over several sequences; faster memory reads speed up every step; prompt caching removes prefill work entirely. The route name is irrelevant.

Exercise 4one answer

Why does the course build with xcodebuild instead of swift build?

MLX's GPU kernels are Metal shaders. SwiftPM on the command line cannot compile them into the library MLX loads at run time, so the build must go through Xcode's build system.
