16. Mixture of experts

Replace the MLP with many expert MLPs and a router that picks a few per token. Implement routing, gathered matrix multiplies and expert stacking, and verify them against tiny random checkpoints you can run on any Mac.

By the end of this lesson you can

  • Explain how a mixture-of-experts layer chooses and mixes experts
  • Implement expert weights as one stacked tensor with gathered matmuls
  • Explain why prefill sorts tokens by expert
  • Convert per-expert checkpoint tensors into the stacked layout
  • Reason about the memory and speed of MoE models on a Mac

The idea

A dense model uses every parameter for every token. A mixture-of-experts (MoE) model replaces the MLP in some or all blocks with E separate expert MLPs and a small router, a linear layer that scores each expert for each token. Only the top k experts run, and their outputs are mixed by the router's scores.

Qwen3-30B-A3B is the standard example: 128 experts per layer, 8 active per token, about 30 billion parameters in total and about 3 billion active. For an inference server on a Mac this is a very interesting trade:

  • Memory must hold all 30B parameters: about 17 GB at 4.5 bits per weight. That needs a 32 GB Mac.
  • Bandwidth, Lesson 2's speed limit, only has to cover the active 3B per token: about 1.7 GB. So it decodes about as fast as a 3B dense model while being much more capable.

Unified memory makes Macs unusually good at MoE models: large RAM, moderate bandwidth, which is exactly what an MoE needs.

Routing

code/Sources/Inference/SwitchLayers.swiftswift
/// Mixture-of-experts feed-forward layer.
///
/// A router scores all experts for each token, keeps the top `k`, and mixes
/// their outputs by the renormalized scores. Qwen3.5 adds a shared expert
/// that every token uses, scaled by its own learned gate.
final class SparseMoE: Module, UnaryLayer {
    let topK: Int
    let normalizeTopK: Bool

    @ModuleInfo(key: "gate") var router: Linear
    @ModuleInfo(key: "switch_mlp") var experts: SwitchGLU
    @ModuleInfo(key: "shared_expert") var sharedExpert: Qwen35MLP?
    @ModuleInfo(key: "shared_expert_gate") var sharedExpertGate: Linear?

    init(hidden: Int, intermediate: Int, experts: Int, topK: Int, normalizeTopK: Bool, sharedIntermediate: Int?) {
        self.topK = topK
        self.normalizeTopK = normalizeTopK
        _router.wrappedValue = Linear(hidden, experts, bias: false)
        _experts.wrappedValue = SwitchGLU(hidden: hidden, intermediate: intermediate, experts: experts)
        if let sharedIntermediate {
            _sharedExpert.wrappedValue = Qwen35MLP(hidden: hidden, intermediate: sharedIntermediate)
            _sharedExpertGate.wrappedValue = Linear(hidden, 1, bias: false)
        }
    }

    func callAsFunction(_ x: MLXArray) -> MLXArray {
        let probs = softmax(router(x).asType(.float32), axis: -1)
        let indices = argPartition(probs, kth: -topK, axis: -1)[.ellipsis, (-topK)...]
        var scores = takeAlong(probs, indices, axis: -1)
        if normalizeTopK {
            scores = scores / scores.sum(axis: -1, keepDims: true)
        }

        var y = (experts(x, indices) * scores[.ellipsis, .newAxis]).sum(axis: -2).asType(x.dtype)
        if let sharedExpert, let sharedExpertGate {
            y = y + sigmoid(sharedExpertGate(x)) * sharedExpert(x)
        }
        return y
    }
}
  1. Score. The router maps each token's hidden vector to E logits; softmax, in float32, gives probabilities.
  2. Select. argPartition finds the top k experts per token without sorting all of them.
  3. Renormalize. With norm_topk_prob, the k selected scores are rescaled to sum to 1.
  4. Run and mix. Each token goes through its k experts, giving [B, L, k, hidden]; the outputs are weighted by the scores and summed over k.
  5. Shared expert (Qwen3.5). One more MLP runs for every token, scaled by its own sigmoid gate, and is added. It captures what every token needs, so the routed experts can specialize.

The layer conforms to UnaryLayer, so it drops into the mlp slot of a block. In Qwen3 the config decides per layer:

Experts as one tensor

Storing 128 separate Linear layers and looping over them per token would be hopelessly slow. Instead, all experts' weights for one projection are one tensor of shape [E, out, in], and MLX's gatherMM multiplies each input row by the expert matrices its indices name, in one kernel:

code/Sources/Inference/SwitchLayers.swiftswift
/// A bank of `E` linear layers stored as one `[E, out, in]` tensor. Each
/// input row is multiplied only by the experts its indices name, so the
/// cost scales with the experts used, not the experts that exist.
public class SwitchLinear: Module, Quantizable {
    @ParameterInfo(key: "weight") var weight: MLXArray

    init(inputDims: Int, outputDims: Int, experts: Int) {
        _weight.wrappedValue = MLXArray.zeros([experts, outputDims, inputDims])
    }

    /// `x`: `[..., 1, in]`, `indices`: `[..., k]`. Returns `[..., k, out]`.
    func callAsFunction(_ x: MLXArray, _ indices: MLXArray, sorted: Bool) -> MLXArray {
        gatherMM(x, weight.swappedAxes(-1, -2), rhsIndices: indices, sortedIndices: sorted)
    }

    public func toQuantized(groupSize: Int, bits: Int, mode: QuantizationMode) -> Module {
        QuantizedSwitchLinear(self, groupSize: groupSize, bits: bits, mode: mode)
    }
}
code/Sources/Inference/SwitchLayers.swiftswift
public final class QuantizedSwitchLinear: SwitchLinear, Quantized {
    @ParameterInfo(key: "scales") var scales: MLXArray
    @ParameterInfo(key: "biases") var biases: MLXArray?
    public let groupSize: Int
    public let bits: Int
    public let mode: QuantizationMode

    init(_ other: SwitchLinear, groupSize: Int, bits: Int, mode: QuantizationMode) {
        self.groupSize = groupSize
        self.bits = bits
        self.mode = mode
        let q = quantized(other.weight, groupSize: groupSize, bits: bits, mode: mode)
        _scales.wrappedValue = q.scales
        _biases.wrappedValue = q.biases
        super.init(inputDims: 0, outputDims: 0, experts: 0)
        self.weight = q.wq
        self.freeze()
    }

    override func callAsFunction(_ x: MLXArray, _ indices: MLXArray, sorted: Bool) -> MLXArray {
        gatherQuantizedMM(
            x, weight, scales: scales, biases: biases, rhsIndices: indices,
            transpose: true, groupSize: groupSize, bits: bits, mode: mode, sortedIndices: sorted)
    }
}

The layer conforms to Quantizable, so the generic quantize(model:) walk from Lesson 4 turns it into a QuantizedSwitchLinear, whose call uses gatherQuantizedMM on packed 4-bit weights. Three of them make a SwiGLU expert bank:

code/Sources/Inference/SwitchLayers.swiftswift
/// SwiGLU MLPs for `E` experts. Each token runs through the `k` experts it
/// was routed to.
final class SwitchGLU: Module {
    @ModuleInfo(key: "gate_proj") var gateProj: SwitchLinear
    @ModuleInfo(key: "up_proj") var upProj: SwitchLinear
    @ModuleInfo(key: "down_proj") var downProj: SwitchLinear

    init(hidden: Int, intermediate: Int, experts: Int) {
        _gateProj.wrappedValue = SwitchLinear(inputDims: hidden, outputDims: intermediate, experts: experts)
        _upProj.wrappedValue = SwitchLinear(inputDims: hidden, outputDims: intermediate, experts: experts)
        _downProj.wrappedValue = SwitchLinear(inputDims: intermediate, outputDims: hidden, experts: experts)
    }

    /// `x`: `[B, L, hidden]`, `indices`: `[B, L, k]`. Returns `[B, L, k, hidden]`.
    func callAsFunction(_ x: MLXArray, _ indices: MLXArray) -> MLXArray {
        let (B, L, k) = (indices.dim(0), indices.dim(1), indices.dim(2))
        var x = expandedDimensions(x, axes: [-2, -3])   // [B, L, 1, 1, hidden]

        // With many tokens (prefill), group rows by expert so each expert's
        // weights are read once, then restore the original order.
        let sort = indices.size >= 64
        var idx = indices
        var inverse: MLXArray?
        if sort {
            let flat = indices.flattened()
            let order = argSort(flat)
            inverse = argSort(order)
            x = x.flattened(start: 0, end: -3)[order.floorDivide(k)]
            idx = flat[order]
        }

        let h = swiglu(gateProj(x, idx, sorted: sort), upProj(x, idx, sorted: sort))
        var y = downProj(h, idx, sorted: sort)

        if let inverse {
            y = y[inverse].reshaped(B, L, k, 1, -1)
        }
        return y.squeezed(axis: -2)
    }
}

The sorting step matters for prefill. With hundreds of tokens each picking 8 experts, rows for any given expert are scattered all over the batch, and the kernel would load each expert's weights many times. Sorting the (token, expert) pairs by expert makes all rows for one expert contiguous, so its weights are read once; sortedIndices: true tells the kernel it may rely on that. An inverse permutation restores the original order afterwards. During decode there are only k pairs per token, so sorting is skipped below 64 pairs.

Loading expert weights

Hugging Face checkpoints store each expert separately: mlp.experts.17.gate_proj.weight, 128 times per projection per layer. The loader stacks them into the layout above before updating the model:

code/Sources/Inference/SwitchLayers.swiftswift
/// Hugging Face checkpoints store each expert separately
/// (`mlp.experts.{e}.gate_proj.weight`). Stack them into the single
/// `[E, out, in]` tensor that `SwitchLinear` expects.
func stackExperts(_ weights: inout [String: MLXArray]) {
    let pattern = /^(.*)\.experts\.(\d+)\.(gate_proj|up_proj|down_proj)\.weight$/
    var groups = [String: [Int: MLXArray]]()
    for (name, array) in weights {
        guard let m = name.wholeMatch(of: pattern) else { continue }
        groups["\(m.1).switch_mlp.\(m.3).weight", default: [:]][Int(m.2)!] = array
        weights[name] = nil
    }
    for (name, experts) in groups {
        weights[name] = stacked((0 ..< experts.count).map { experts[$0]! })
    }
}

Both loaders call it, for the main model and for the MTP head (whose single layer is also MoE in Qwen3.5 MoE models). Pre-converted MLX checkpoints already contain stacked switch_mlp tensors and pass through untouched.

Verifying without a 30B model

The real MoE models do not fit on the 8 GB M1 this course was built on. The fix is a standard testing trick: tiny checkpoints with the exact architecture and random weights. yujiepan/qwen3-moe-tiny-random (hidden size 64, 8 experts, top-2, one dense and one MoE layer) and yujiepan/qwen3.5-moe-tiny-random (hidden size 8, 128 experts, top-10, a shared expert, linear attention and an MoE MTP head) are a few megabytes each, but they exercise every code path: routing, stacking, gathered matmuls, sorting during prefill, and the loaders.

qwen3-moe-tiny-random     max |Δ logit| 0.0625   (logits up to 9.9)   argmax agrees at every position
qwen3.5-moe-tiny-random   max |Δ logit| 0.043    (logits up to 1.4)   argmax agrees at every position

One surprise: Python's mlx-lm could not load the Qwen3.5 tiny checkpoint at all, because its loader expects the experts in a fused layout and this checkpoint stores them per expert. The reference run had to stack them by hand first. Your own loader handling both layouts is a small advantage of writing it yourself.

Random weights make a strict test: there are no learned regularities to hide errors behind, so a wrong routing or a transposed tensor shows up immediately as large differences.

Lesson in one breath

An MoE layer scores all experts per token, keeps the top k, and adds their outputs weighted by renormalized scores; Qwen3.5 adds a shared expert every token uses. Expert weights live in one [E, out, in] tensor and gatherMM multiplies each token only by its chosen experts. A 30B-A3B model needs memory for 30B parameters but reads only about 3B per token, so it decodes like a small model if it fits.
