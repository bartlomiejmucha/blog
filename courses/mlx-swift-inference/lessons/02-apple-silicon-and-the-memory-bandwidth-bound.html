2. Apple Silicon and the memory-bandwidth bound

Generating one token means reading every weight of the model once. On a Mac that makes memory bandwidth, not compute, the speed limit, and it explains almost every design choice in this course.

By the end of this lesson you can

  • Estimate a model's decode speed from its size and the chip's memory bandwidth
  • Explain why decode is bandwidth-bound and prefill is compute-bound
  • Say what unified memory changes, and what it does not
  • Explain why MLX is a good fit for an inference server on a Mac

What one token costs

Lesson 1 said each new token costs one forward pass. Look at what that pass does. Almost all of a transformer's work is matrix-vector multiplication: a vector for the current token is multiplied by weight matrices, layer after layer. For each weight, the GPU must

  1. load the weight from memory, and
  2. do one multiply and one add with it: 2 floating-point operations.

So decoding one token with a model of N parameters moves about N × bytes per weight bytes and does about 2N operations. For Qwen3.5-0.8B with 4-bit weights, that is roughly 0.45 GB read and 1.6 billion operations per token.

Which of the two is the bottleneck depends on the chip. A base M1 can read memory at about 68 GB/s (we measured 52 GB/s achieved by MLX's quantized kernel) and do about 1.45 trillion float32 operations per second (measured with a 4096×4096 matrix multiply). Reading 0.45 GB takes about 8.7 ms at 52 GB/s. Doing 1.6 billion operations takes about 1.1 ms. The GPU spends most of each step waiting for memory.

Arithmetic intensity

The general tool here is arithmetic intensity: operations performed per byte moved. Every chip has a balance point, its peak operations per second divided by its bandwidth. For the M1, about 1.45 TFLOPS / 60 GB/s ≈ 24 operations per byte. Work below that is bandwidth-bound; work above it is compute-bound.

Prefill multiplies a whole matrix of token vectors by each weight matrix, so each weight that is read is used hundreds of times. That is why a 512-token prefill takes about 0.75 s on the M1, not 512 × 11 ms ≈ 5.6 s.

The decode row is the important one. Any technique that does more useful work per weight read is a direct speed-up: quantization shrinks the bytes; batching serves several sequences per read (Lesson 15); speculative decoding checks several tokens of one sequence per read (Lessons 18 and 19). The rest of this course keeps coming back to this table.

Estimate it yourself

The rule of thumb: decode tokens per second ≈ achievable bandwidth ÷ bytes read per token. Achievable bandwidth is usually 70–85% of the advertised figure. Bytes per token is the weight size, plus a little for the KV cache, which grows with context.

Try it below. On the M1, the 0.8B model at 4 bits gives a ceiling of about 113 tokens per second; the finished server reaches about 90. The gap is real work the rule ignores: the 248,000-row output projection, attention over the cache, dozens of small kernel launches per layer, and CPU time between steps. Lesson 20 measures each of these.

Decode speed ceiling

Pick a chip, a model size and a weight precision. The bar is bandwidth ÷ bytes per token, at 75% of the advertised bandwidth.

Unified memory

On a PC with a discrete GPU, the model lives in the GPU's own memory, and anything the CPU produces must be copied across a PCIe bus. Apple Silicon has unified memory: CPU and GPU share the same physical RAM. Three consequences matter for us:

  • No copies. An array written by the CPU (token ids, a sampled token) is visible to the GPU without a transfer. MLX arrays are not tied to a device; you choose where an operation runs, not where data lives.
  • Model size is limited by RAM. A 16 GB Mac can hold models that would not fit on a 12 GB graphics card. But macOS keeps part of RAM for itself and caps how much the GPU may use by default, so plan on roughly two thirds of RAM for weights and caches.
  • Bandwidth is shared. The same memory system serves the CPU, the GPU and everything else running. A busy browser can slow decode measurably. Benchmark on a quiet machine.

Why MLX

MLX is Apple's array framework for machine learning on Apple Silicon. It has a NumPy-like API in Python, C++ and Swift, and it was designed around unified memory. For an inference server it gives us:

  • Metal kernels for the hot paths: quantized matrix multiplication, fused attention, RMSNorm and RoPE, all tuned for Apple GPUs.
  • Lazy evaluation: operations build a graph that runs when a result is needed. That lets you queue the next step on the GPU while the CPU does other work (Lesson 3).
  • A native Swift API, so the model, the scheduler and the HTTP server are one process in one language with no Python runtime.
  • Custom kernels written inline in Metal when nothing built-in fits. Lesson 17 writes one for Qwen3.5's linear attention.

The alternatives are worth knowing. llama.cpp is a mature C++ engine with its own file format (GGUF). Core ML targets the Neural Engine but is awkward for autoregressive generation. The Python mlx-lm package is the reference this course checks its numbers against. Building on raw MLX Swift is the right choice here because the goal is to understand and control every part.

Lesson in one breath

Decoding one token reads all the weights once and does about two floating-point operations per weight. That is far too little arithmetic per byte to keep the GPU busy, so decode speed is roughly memory bandwidth divided by model size. Prefill processes many tokens per weight read and is limited by compute instead. Shrinking the bytes (quantization) or sharing each read across more tokens (batching, speculative decoding) are the levers.

Exercise 2one answer

Why is prefill much faster per token than decode?

During prefill the whole prompt is multiplied by each weight matrix at once. One read serves hundreds of tokens, so arithmetic, not memory, becomes the limit.

A chip does 4 TFLOPS and reads 200 GB/s. What is its balance point in operations per byte?

4 × 1012 ÷ 200 × 109 = 20 operations per byte. Single-sequence decode at about 4 ops/byte sits far below it, so it is bandwidth-bound.
