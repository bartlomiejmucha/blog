4. Modules, parameters and fast kernels

Neural network code in MLX is a tree of modules whose parameter names match the checkpoint. Learn that tree, quantized layers, compile, the fused fast kernels, and how to write your own Metal kernel.

By the end of this lesson you can

  • Write an MLXNN module whose parameter names match a checkpoint
  • Load weights with update(parameters:verify:) and know what verify catches
  • Describe what a QuantizedLinear stores
  • Use compile to fuse elementwise work
  • Use the fast RMSNorm, RoPE and attention kernels, and write a custom Metal kernel

Modules are named trees

A model is a tree of Module objects. Each one owns parameters (arrays) and child modules. The key fact for an inference engine is that the dotted path of every parameter is its name in the checkpoint.

code/Sources/mlx-basics/main.swiftswift
/// A tiny two-layer network. Property keys are the names checkpoints use.
final class TinyMLP: Module, UnaryLayer {
    @ModuleInfo(key: "up_proj") var up: Linear
    @ModuleInfo(key: "down_proj") var down: Linear

    init(dims: Int, hidden: Int) {
        _up.wrappedValue = Linear(dims, hidden, bias: false)
        _down.wrappedValue = Linear(hidden, dims, bias: false)
    }

    func callAsFunction(_ x: MLXArray) -> MLXArray {
        down(silu(up(x)))
    }
}

@ModuleInfo(key: "up_proj") says: this child appears as up_proj in the parameter tree. The Swift property can have any name you like (up), but the key must match the checkpoint exactly. Qwen's real MLP is the same shape with three projections, and its parameters are called model.layers.3.mlp.up_proj.weight because the module tree nests: model → layers → index 3 → mlp → up_proj → weight.

Implement callAsFunction and the module can be called like a function. Conforming to UnaryLayer (one array in, one array out) lets you store different implementations behind one property, which Lesson 16 uses to swap a dense MLP for a mixture-of-experts layer.

Loading weights

code/Sources/mlx-basics/main.swiftswift
func modulesAndParameters() throws {
    let mlp = TinyMLP(dims: 8, hidden: 32)
    for (name, array) in mlp.parameters().flattened() {
        print(name, array.shape)          // down_proj.weight [8, 32], up_proj.weight [32, 8]
    }
    // Loading weights is a dictionary update keyed by those names.
    let weights: [String: MLXArray] = [
        "up_proj.weight": MLXArray.zeros([32, 8]),
        "down_proj.weight": MLXArray.zeros([8, 32]),
    ]
    try mlp.update(parameters: ModuleParameters.unflattened(weights), verify: [.all])
    print(mlp(MLXArray.ones([1, 8])).sum().item(Float.self))  // 0.0
}

parameters().flattened() lists the tree as (path, array) pairs. Loading is the reverse: build a flat [String: MLXArray] dictionary, turn it into a tree with ModuleParameters.unflattened, and update the module.

Always pass verify: [.all]. It throws if the dictionary has a key the model lacks, if the model has a parameter the dictionary lacks, or if a shape does not match. Without it, a typo in a key silently leaves that layer with its initial values, and the model produces fluent-looking garbage that is very hard to debug. With it, the first run tells you exactly which name is wrong.

Quantized layers

code/Sources/mlx-basics/main.swiftswift
func quantizedLinear() {
    let linear = Linear(256, 512, bias: false)
    let q = QuantizedLinear(linear, groupSize: 64, bits: 4)
    print(q.weight.shape, q.weight.dtype)  // [512, 32] uint32: 8 four-bit values per word
    print(q.scales.shape)                  // [512, 4]: one scale per group of 64
    let x = MLXArray.ones([1, 256])
    let error = abs(q(x) - linear(x)).max().item(Float.self)
    print("max error from 4-bit:", error)
}

A QuantizedLinear stores the same matrix in three arrays:

  • weight: 4-bit integers packed eight to a UInt32, so a 512×256 matrix becomes 512×32 words;
  • scales and biases: one of each per group of 64 consecutive weights in a row, in bfloat16.

Each real weight is reconstructed as scale × q + bias, with q an integer from 0 to 15. The fast kernels never rebuild the full matrix: they unpack, scale and multiply in registers as they stream the packed weights from memory. That is the whole point, because Lesson 2 showed that the bytes read are the cost. Lesson 5 covers the format in detail.

The module-level quantize(model:filter:) function walks a model and replaces every Linear and Embedding the filter accepts with its quantized version. Our loaders use it to match a pre-quantized checkpoint, or to quantize a full-precision one while loading.

compile: fusing elementwise work

code/Sources/mlx-basics/main.swiftswift
func compiledFunctions() {
    // Elementwise steps run as separate kernels, each one reading and
    // writing the whole array...
    let gate = MLXRandom.normal([1, 4096]).asType(.bfloat16)
    let up = MLXRandom.normal([1, 4096]).asType(.bfloat16)
    let plain = silu(gate) * up
    // ...compile() traces the function once and fuses them into one kernel.
    let fused = compile(shapeless: true) { (g: MLXArray, u: MLXArray) in silu(g) * u }
    let diff = abs(plain.asType(.float32) - fused(gate, up).asType(.float32)).max()
    print("max difference:", diff.item(Float.self))   // 0.0: same math, fewer memory round trips
}

Each MLX operation normally becomes its own GPU kernel, which reads its inputs from memory and writes its output back. For elementwise chains like silu(gate) * up, that means several full passes over the data. compile traces the function once and emits a single fused kernel, which reads each input once and writes once. shapeless: true lets one compiled function serve every input shape, which matters because sequence lengths change all the time.

The model code in this course compiles exactly this swiglu function, matching the Python reference. Compilation is a performance tool here: the fused and unfused results are identical in this example.

The fast kernels

Three operations dominate a transformer layer apart from the matrix multiplies, and MLX ships hand-written Metal kernels for each:

code/Sources/mlx-basics/main.swiftswift
func fastKernels() {
    let x = MLXRandom.normal([1, 8, 16, 64])          // [batch, heads, tokens, headDim]
    let w = MLXArray.ones([64])
    let n = MLXFast.rmsNorm(x, weight: w, eps: 1e-6)
    let r = MLXFast.RoPE(n, dimensions: 64, traditional: false, base: 10_000, scale: 1, offset: 0)
    let out = MLXFast.scaledDotProductAttention(
        queries: r, keys: r, values: x, scale: 1 / 8, mask: .causal)
    print(out.shape)                                   // [1, 8, 16, 64]
}
  • MLXFast.rmsNorm normalizes each vector by its root-mean-square and scales it by a learned weight, in one pass.
  • MLXFast.RoPE rotates pairs of dimensions by angles that depend on the token's position. offset is the position of the first token in the array, which is how a cached decode step knows it is at position 517 and not 0.
  • MLXFast.scaledDotProductAttention computes softmax(QKᵀ·scale + mask)·V without materializing the full score matrix. Its mask argument takes .causal (each position attends only to itself and earlier ones), .none, or an explicit array. It also handles grouped-query attention, where several query heads share one key/value head, by itself.

Your own Metal kernel

When no built-in operation does what you need efficiently, MLXFast.metalKernel compiles a Metal function from a string at run time:

code/Sources/mlx-basics/main.swiftswift
func customKernel() {
    // One GPU thread per element. MLX generates the function signature from
    // the input and output names; the body is plain Metal.
    let kernel = MLXFast.metalKernel(
        name: "scaled_add",
        inputNames: ["a", "b"],
        outputNames: ["out"],
        source: """
            uint i = thread_position_in_grid.x;
            out[i] = a[i] * 2.0 + b[i];
            """)
    let a = MLXArray([1, 2, 3, 4] as [Float])
    let b = MLXArray([10, 10, 10, 10] as [Float])
    let out = kernel([a, b], grid: (4, 1, 1), threadGroup: (4, 1, 1),
                     outputShapes: [[4]], outputDTypes: [.float32])
    print(out[0])                                      // [12, 14, 16, 18]
}

You write only the body. MLX generates the function signature from the input and output names, passes each input as a device pointer, and lets you set template parameters (types and integer constants) per call. grid is the total number of threads and threadGroup how many run together and can share fast memory.

This looks like a curiosity now. In Lesson 17 it is essential: Qwen3.5's linear-attention recurrence written with ordinary operations launches several kernels per token, and a custom kernel that keeps the state in registers makes prefill about 3× faster.

Lesson in one breath

A Module's parameters form a tree whose dotted paths are the checkpoint's tensor names; @ModuleInfo(key:) sets each name. Loading weights is a dictionary update, and verify: [.all] turns naming mistakes into immediate errors. Quantized layers replace a weight with packed integers plus per-group scales and biases. compile fuses elementwise operations, and MLXFast provides fused kernels for the transformer's hot paths.

A module has @ModuleInfo(key: "self_attn") var attention: Attention, and Attention has @ModuleInfo(key: "q_proj") var q: Linear. The parent is stored in a model under layers.0. What is the full name of the query weight?

Exercise 2one answer

Your loader misspells a key, mlp.gate_prj.weight. What does update(parameters:verify: [.all]) do?

verify .all rejects extra keys, missing parameters and shape mismatches, so naming errors surface at load time instead of as garbage output.

Exercise 3compute it

A 4096×4096 weight is quantized to 4 bits with group size 64 and bfloat16 scales and biases. How many megabytes (106 bytes) do the scales and biases take together? Two decimals.

Each row has 4096 / 64 = 64 groups, so 4096 × 64 = 262,144 groups. Each group stores one scale and one bias at 2 bytes each: 262,144 × 4 = 1,048,576 bytes ≈ 1.05 MB. The packed weights themselves take 4096 × 4096 / 2 = 8 MB.

Exercise 4one answer

What does offset do in MLXFast.RoPE(x, ..., offset: 517)?

RoPE angles depend on absolute position. During decode, the single new token sits after everything in the cache, so its position is the cache length.

Exercise 5one answer

Why does compiling silu(gate) * up make it faster?

Elementwise work is memory-bound. Fusing removes the intermediate round trips through memory.
