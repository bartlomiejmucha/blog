4. Neurons, matrices and nonlinearity

The last two lessons turned text into numbers and showed how numbers compare. But nothing in them yet changes a number — and the model is nothing but chained changes. This lesson builds the smallest possible change-maker, a single neuron, from scratch, then stacks it into the layers that fill a transformer block.

By the end of this lesson you can

  • Compute a single neuron's output by hand, the same way the machine does
  • Read matrix shapes and know which multiplications are even legal
  • Explain why a stack of layers needs activation functions — and what collapses without them
  • Recognise the expand-then-contract shape inside a real transformer block

One neuron

Last lesson ended with the embedding table "handing off" to the transformer blocks. But notice what that handoff actually requires: something that can change the arrows. A lookup table can't — it just reads out a fixed row. The whole model, from the second station onward, is chains of things-that-change-numbers. This lesson builds the smallest one, from scratch.

Here is the whole design of a "neuron" (in quotes because it has nothing to do with biology beyond being small and numerous). It does exactly four arithmetic steps:

  1. Multiply each input by a private number of its own. Those numbers are called weights — one per input, learned during training. A weight is a volume knob: 2.0 means "amplify what this input says", −1.0 means "treat it as evidence against me", 0 means "ignore it".
  2. Add the products up. One number so far: a single verdict compiled from all the inputs.
  3. Add one more learned number, the bias. Think of it as a threshold of doubt: it shifts the verdict up or down before anyone looks at it, deciding how easily this neuron gets excited at all.
  4. Squash the result through a small fixed function — the activation. The standard one, ReLU, just does max(0, result): pass positive numbers through unchanged, clamp negatives to zero. "Silent unless you have something positive to say."

Now do it by hand, with the exact numbers the widget at the end of this section starts on. Input vector [2, 1, 0.5], weights [0.5, −1.0, 2.0], bias 1.0, ReLU:

step 1+2: (0.5×2) + (−1×1) + (2×0.5) = 1 − 1 + 1 = 1
step 3:      1 + bias 1 = 2
step 4:      ReLU(2) = 2  (positive, passes unchanged)
output: 2

That's a neuron. Written as one formula — which is how you'll see it everywhere — the same thing is y = f(w₁x₁ + w₂x₂ + … + b), and now you can read it: products, then sum, then bias, then squash.

And here is the connection to last lesson, which makes this more than arithmetic trivia. Step 1+2 — multiply matching pairs and add — is the dot product you just learned. Remember what a dot product measures: how much two arrows point the same way. So a neuron is really asking: "how much does this input point in my direction?" — where "my direction" is its weight vector, one of thousands of little questions the model learned to ask. The squash (step 4) then decides how loudly to answer: silence, or a number proportional to the match.

In the widget below, drag the input sliders and watch the four steps recompute line by line — then switch the activation to "none" and drag an input until the sum goes negative. That difference is the entire subject of section 3.

Layers are matrix multiplications

One neuron asks one question. A real layer asks thousands, and it asks them all at the same time. Here is how thousands of separate neurons become one object.

Take two neurons that both read the same 3 inputs. Neuron 1 has weights [2, 0, 1]. Neuron 2 has weights [1, 3, 0]. Write one under the other:

neuron 1 →  2  0  1
neuron 2 →  1  3  0

That block of 6 numbers is a matrix: a grid of numbers with a fixed number of rows and columns. Nothing was added or changed — the neurons' weights were simply parked in a grid, one neuron per row. A layer of 11008 neurons is the same grid with 11008 rows.

Now feed it the input vector [1, 2, 0]. Each neuron does its own dot product with that input, exactly as in section 1 — multiply matching positions, add them up:

neuron 1: (1×2) + (2×0) + (0×1) = 2
neuron 2: (1×1) + (2×3) + (0×0) = 7
output: [2, 7]

Three numbers went in, two came out — one per neuron. Doing that for every row of the grid at once is what matrix multiplication means. It is not a new kind of arithmetic; it is the dot product you already know, repeated once per row, with the results collected in order. That is the entire content of "a layer is a matrix multiplication".

The reason it is written that way is speed. A GPU can run all 11008 of those dot products simultaneously if you hand it one grid, and cannot if you hand it 11008 separate neurons. Almost all of an LLM's compute is this single operation, repeated at different sizes.

Two words that are easy to mix up. "Input" gets used both ways: the whole list [1, 2, 0] is the input vector, and each number inside it is one input — so "a neuron with 3 inputs" and "an input vector of length 3" say the same thing. These lessons write input vector when they mean the whole list. The bigger distinction is against the neuron's weights. Both are lists of 3 numbers and they get multiplied pair by pair, but they are opposite kinds of thing: the input vector is data passing through — freshly computed for every token and prompt, and gone once the answer is done. The field calls runtime data like this activations (a second meaning of the same word: in section 1 it named the squashing function, here it names any data flowing through the model). The weights, by contrast, are the neuron itself, learned in training and then frozen. "70 billion parameters" is a count of weights. Nobody counts activations.

Reading shapes

A shape is written [rows, columns]. So [2, 3] means "2 rows of 3 numbers each" — which is exactly our grid of neurons: 2 of them, 3 weights apiece.

A single list of numbers is the case worth pausing on. On the page, [1, 2, 0] is just three numbers in square brackets — that notation says nothing about rows or columns. To put it in a grid you have to choose: lying flat it is one row of three, shape [1, 3]; stood on end it is three rows of one, shape [3, 1].

flat [1, 3]1   2   0
upright [3, 1]1
2
0

Same three numbers, same meaning, two orientations. Which one you want is decided entirely by the rule below.

Here is that rule. Each output number is a dot product, and a dot product only works when both sides have the same length — our neuron has 3 weights, so the input must have 3 numbers, not 2 and not 4. Written as shapes, with the neuron grid on the left, the input has to stand upright so the two 3s meet:

  [2, 3] × [3, 1] → [2, 1]
         the inner pair must match, and cancels

The inner two numbers must be equal; they cancel, and the outer two are the answer's shape. Here that gives [2, 1] — 2 rows of 1 number, our two answers 2 and 7 stood upright.

Both halves of that rule come from one mechanical fact: you always pair a row on the left with a column on the right. Set the two grids next to each other and it is visible:

weights [2, 3]

2   0   1
1   3   0

input [3, 1]

1
2
0

Take row 1, 2 0 1, and the single column, 1 2 0 reading downward. Pair them off by position — 1st with 1st, 2nd with 2nd, 3rd with 3rd — multiply each pair, add the results: 2×1 + 0×2 + 1×0 = 2. Then row 2 against the same column: 1×1 + 3×2 + 0×0 = 7.

Now both halves of the rule explain themselves. The inner numbers must match because you are pairing entries off — a row of 3 needs a column of 3, or some entry has no partner. The outer numbers are the answer's shape because you do exactly one dot product per row-column combination: 2 rows and 1 column means 2 answers. If the right-hand grid had 2 columns you would get 4.

That is the one thing worth practising here. [8, 512] × [512, 2048] → [8, 2048] is legal. [8, 512] × [2048, 512] is not — 512 ≠ 2048, so nothing lines up.

So do neurons go in rows or columns?

Both, depending on which side of the × you put the weights on — and this is the question that trips up everyone reading real code. Take a realistic layer: 4096 numbers in, 11008 neurons. Each neuron still has one weight per input, so 4096 weights apiece. The only constraint is that its 4096 weights must lie along the axis that touches the input, because that is where the dot product happens:

Written asShapesOne neuron is
x · W[1, 4096] × [4096, 11008] → [1, 11008]a column of 4096
W · x[11008, 4096] × [4096, 1] → [11008, 1]a row of 4096

Same arithmetic, same 11008 output numbers, both times. Write the shapes down and the two 4096s have to end up next to each other; that alone tells you which way the rectangle is drawn. So "row or column" is not a fact about neurons — it is a fact about the notation.

Where this actually bites: PyTorch's nn.Linear(4096, 11008) stores its weights as [11008, 4096] — neurons as rows — but computes x · Wᵀ, flipping them to columns on the way in. Storage convention and multiply convention disagree inside the same call. Always check which one a shape is describing.

A's two rows are a small version of something real: a model pushes a whole sentence through a layer in one multiply, one row per token — a [T, d] grid, T tokens by d numbers each.

One warning for when you read code. The widget writes the neurons as columns (xW, weights shaped [in, out]); plenty of papers and codebases write them as rows instead (Wx, weights shaped [out, in]). Same arithmetic, opposite layout — but if you mix the two, every shape you check will look wrong. Check which convention a source uses before trusting its shapes.

Why nonlinearity is not optional

Section 1's widget had a switch you may have flipped: with ReLU on, a negative sum turns into zero; with "none", that same negative number passes straight through untouched. That one difference is the reason stacking layers works at all. Here is why.

What "linear" means

A function is linear when two things hold. Scaling the input scales the output by the same factor: f(3x) = 3·f(x). And splitting the input splits the answer: f(a + b) = f(a) + f(b). Multiplying by 2 passes both tests, and so does matrix multiplication — which is the whole reason the last section worked out so neatly.

ReLU fails the second test, and you can see it in one line:

ReLU(−4 + 6) = ReLU(2) = 2
ReLU(−4) + ReLU(6) = 0 + 6 = 6

Two different answers from the same two numbers. Clamping the −4 to zero threw away something that plain multiplication would have carried through, so the result no longer decomposes. Every activation function is built to fail that test on purpose. The failure is the feature.

What collapses without it

Suppose you dropped the activation and stacked plain matrix multiplies. Two layers in a row is W₂(W₁x). Matrix multiplication is associative — the grouping does not change the answer — so W₂(W₁x) equals (W₂W₁)x. Multiply the two weight matrices together once, in advance, and you have a single matrix that does the entire two-layer job in one step.

Nothing stops at two. Thirty-two stacked layers fold into one matrix the same way. The model would have exactly the expressive power of a single layer no matter how deep you built it, so depth would buy nothing. Biases do not rescue it either: a stack of "multiply then add" steps collapses to one multiply plus one add.

Put ReLU between them and W₂·ReLU(W₁x) cannot be folded into any single matrix, because the clamping happens partway through and no matrix clamps. That is the entire job of the activation: stop each layer dissolving into the one before it.

What the bending buys

Blocking the collapse is the mechanical answer. The useful answer is what depth can then do that one layer cannot.

A linear map is limited in a specific way. It can stretch the space, rotate it, shear it, flatten it — but straight lines come out straight and parallel lines stay parallel. So it can only ever separate groups of points that a single straight cut could already separate.

Plenty of real questions are not like that. Picture two kinds of point on a plane, one kind ringed around the other. No straight line splits them, and no amount of stretching or rotating changes that. Bend the plane once, though, and the inner group lifts clear of the outer one, where a straight cut does work. Each activation adds one more bend, and a model's judgements are built out of many bends stacked up.

The ones you will actually meet

They differ only in how they bend, not in whether. The figure below plots four curves — ReLU, GELU, SiLU and tanh — which between them cover all four entries here:

  • ReLU — max(0, x). The workhorse: cheap to compute, and it is what made deep networks trainable in the first place. Its flaw has a name, the dying ReLU: a neuron whose sum lands in the negative region outputs zero whatever arrives, so it stops influencing anything and stops learning. The neuron widget in section 1 lets you push one into that state.
  • GELU — ReLU with a soft knee: small negatives slip through faintly instead of being clamped flat, which keeps those neurons alive. The default in GPT-family models.
  • SwiGLU — used in Llama and most current open models. Not a single function but a wiring pattern, which is why it has no curve of its own on the plot: it splits the layer's numbers into two halves and lets one half act as a volume knob on the other. The reasoning is that whether a fact matters usually depends on some second fact, and multiplying the two halves together expresses exactly that. It needs three weight matrices instead of two, so implementations shrink the hidden width (to about ⅔ × 4 × d_model) to keep the parameter count level, and still score better. The curve it is built from is SiLU, x·sigmoid(x), the soft-knee shape plotted below.
  • tanh — the pre-2012 default, plotted for contrast. It squeezes every input into the range −1 to +1, which sounds tidy until you look at the ends of the curve: push the input far in either direction and the output stops responding almost entirely. A neuron out there barely reacts to being corrected, so learning crawls. Getting away from that flatness is why the field moved to ReLU.

What this looks like in a real model

Step back and look at what you can now build. A layer is: multiply by a weight matrix, add a bias, apply an activation. That is a complete working component, and two of them stacked back to back make up one of the two halves of every transformer block. A transformer block is the "actual thinking" unit from Lesson 1's assembly line, and it has two halves: this feed-forward part, where each position does some private number-crunching, and attention, where words consult each other. That second half is next lesson.

Before sizing it, though, it is worth joining this lesson to the previous two, because everything below talks about vectors arriving and leaving, and it should be clear where from and where to.

Where this sits in the pipeline

Take the prompt The cat sat and follow it through everything the course has covered so far:

  1. The tokenizer splits it into 3 tokens — The,  cat,  sat — and looks each one up in the vocabulary, giving 3 ids (lesson 2).
  2. Each id selects one row of the embedding table, and each row is 4096 numbers. Three tokens, so 3 vectors of 4096 (lesson 3).
  3. Those 3 vectors are stacked into a grid, one row per token: [3, 4096]. That grid is what enters the first transformer block.
  4. The block does its work and produces a grid of exactly the same size, [3, 4096]. That output becomes the input of block 2, which hands to block 3, and so on through all 32.
  5. What comes out of the last block is turned into a prediction for the next token (lesson 9).

Why 32 blocks? For the same reason the width is 4096: somebody chose it. Depth is a dial, tuned by experiment, and it moves with size — a 7-billion-parameter model is typically 32 blocks of width 4096, a 70-billion one 80 blocks of width 8192, and GPT-3 was 96 blocks of width 12288. Lesson 13 covers how those two dials are traded off against each other. Everywhere this course says "4096 wide, 32 blocks", it means a model of roughly 7 billion parameters.

So yes: the vector that came out of the embedding table is the input vector of this lesson, for the first block. From block 2 onward, the input vector is whatever the block below produced — the same 4096 numbers' worth of space, but with different contents each time, because every block has rewritten them a little. That is all "arrives from the previous block" means.

Two details to keep straight. First, inside a block, attention runs before the feed-forward part, so what actually reaches these matrices is the vector after attention has already updated it; lesson 8 wires the block up exactly. Second, this is a lot of numbers to keep track of by hand, and it does not need to be: the only thing this section needs from the pipeline is that a 4096-number vector goes in and a 4096-number vector must come out.

All the tokens go through together

A natural assumption is that a 3-token prompt runs through the model 3 times, once per token. It does not. All 3 rows travel through every block in one pass, in the same matrix multiplies — that is what the [3, 4096] grid is for, and with a 500-token prompt it is a [500, 4096] grid handled the same way. Section 2's point about batching a whole sentence into one multiply is this, and it is why a GPU is the right hardware.

(Generating a reply is one token at a time, since each new token depends on the one before it. But the prompt itself goes through in a single pass, and lesson 11 shows how the tokens already processed are cached (the KV cache) so they never have to be redone.)

The size that is fixed

A vector of 4096 numbers arrives from the previous block, and whatever comes out has to be 4096 numbers again. The reason is stacking: the next block expects exactly what this one was handed, and a 32-block model only works if every block passes on the same shape it received. So 4096 in, 4096 out. That is not negotiable.

The size that is free

You could satisfy that with a single layer of 4096 neurons. Nobody does. Use two layers instead and something opens up: the first layer can have however many neurons you like, because the second layer's job is to bring the count back down to 4096 whatever the first one produced. The width in the middle is yours to choose.

So choose it larger. Each neuron asks one learned question, so more neurons in the middle means more questions asked before the answer is compiled. Think of that middle layer as a row of inspectors: 4096 numbers arrive, and each inspector checks them for one specific thing ("is this heading toward a verb?", "does this look like the second half of a phone number?" — the questions are learned, not designed, and rarely correspond to anything nameable in English). Every inspector who finds something adds a note. The second layer is then the editor, deciding which of those notes matter enough to pass on. Too few inspectors and the questions go unasked; without the editor, every note gets shouted downstream at full volume.

How much larger? Four times is the long-standing default: 16384 in the middle for a model 4096 wide. Like d_model itself, it is a dial set by experiment rather than derived from anything.

One thing "widen" should not suggest: nothing grows while the model is running. The width is fixed when the model is designed, and the weights that do the widening are learned during training and frozen afterwards. At the moment a prompt goes through, the wide middle is just a rectangle of numbers that was already sitting there.

The finished component

Those two layers together have a name — the feed-forward network, or FFN — and now the formula for it should read as a description of something you already decided on:

FFN(x) = W_down · activation(W_up · x)

Work outward from the innermost bracket, since that is the order things happen in. W_up is the first layer, taking 4096 numbers to 16384. The activation squashes each of those 16384 on its own. W_down is the second layer, bringing 16384 back to 4096. The names say what they do: up into the wide middle, down out of it. (The weights sit on the left of x here, so each neuron is a row — the Wx convention from section 2. Biases are left out to keep the formula readable; some models have them, most recent ones do not.)

This is what the shape rule was for, so check it:

W_up   [16384, 4096] × [4096, 1] → [16384, 1]
W_down [4096, 16384] × [16384, 1] → [4096, 1]

Inner numbers match and cancel, twice, and the vector that comes out is the same size as the one that went in — which was the requirement we started from.

4096 and 16384 are too large to picture, so here is the same component built at a size you can check by hand. Take d_model = 2 instead of 4096, which makes the hidden width 4 × 2 = 8, and run the prompt The cat sat through it. The embedding table hands over three vectors of 2 numbers each:

The  [1, 0]
cat  [0, 2]
sat  [1, 1]    a [3, 2] grid

W_up is [8, 2]: eight neurons, two weights each, sixteen learned numbers in total. Here they are, and push The = [1, 0] through them:

n1  [ 1,  0] · [1, 0] =  1  → ReLU →  1
n2  [ 0,  1] · [1, 0] =  0  → ReLU →  0
n3  [ 1,  1] · [1, 0] =  1  → ReLU →  1
n4  [ 1, −1] · [1, 0] =  1  → ReLU →  1
n5  [−1,  1] · [1, 0] = −1  → ReLU →  0
n6  [ 2,  0] · [1, 0] =  2  → ReLU →  2
n7  [ 0, −1] · [1, 0] =  0  → ReLU →  0
n8  [−1, −1] · [1, 0] = −1  → ReLU →  0

Two numbers in, eight out. Now run the other two tokens through the same eight neurons, and put W_down (two neurons of eight weights, [2, 8]) on the end to bring each row back to 2. So you can check every number yourself, let those two neurons be simple: the first output number is the sum of the answers of n1 and n6; the second, the sum of n3 and n5. (A real W_down reads all eight answers, one weight per inspector — "sum two of them" is a simplification used here only so nothing is hidden from you.) The whole trace, written token-by-row — the xW layout from section 2, tokens as rows, the same numbers in the opposite notation to the formula:

     in [3, 2]      wide [3, 8]         out [3, 2]
The  [1, 0]  →  [1,0,1,1,0,2,0,0]  →  [3, 1]
cat  [0, 2]  →  [0,2,2,0,2,0,0,0]  →  [0, 4]
sat  [1, 1]  →  [1,1,2,0,0,2,0,0]  →  [2, 3]

Four things are visible in that table, and all four hold at full size:

  • Nothing is copied. The arrived as [1, 0], and neither a 1 nor a 0 appears in its eight numbers as such. Each of the eight is a fresh measurement of the original two. Widening does not add information — 8 numbers derived from 2 cannot hold more than the 2 did — it re-describes the same content as answers to eight separate questions.
  • The number of tokens never changes. Three rows in, three rows out. Widening happens along the row, per token: 2 → 8 → 2. The 3 is untouched.
  • One set of weights serves every token. All three rows met the same eight neurons. A fourth token would meet the same eight — no new parameters. The whole component here is 32 learned numbers: 16 in W_up, 16 in W_down.
  • The zeros are the point. Of the 24 hidden numbers, 13 are zero, and which ones differ per token: The silenced n2, n5, n7, n8 while cat silenced n1, n4, n6, n7, n8. That per-token pattern of who spoke is what W_down reads, and it is the only reason a wide middle beats a plain 2 → 2 layer.

Scale every number by 2048 and you have the real thing: [3, 4096] → [3, 16384] → [3, 4096], same in every respect but size.

One position at a time

The table above showed each row handled on its own, and that is not a simplification of the small example — it is how the real thing works. Nothing about cat influenced The. The feed-forward network cannot relate one word to another at all; it takes one position's vector and thinks about it in isolation, and the rows of the grid travel together only for speed.

Relating words is entirely attention's job, in the other half of the block. That division is why a transformer block needs both halves, and it is the thing to carry into the next lesson.

Where the parameters are

Those two matrices are not small. W_up holds 16384 × 4096 ≈ 67 million numbers and W_down holds the same again: about 134 million weights per block, in this one component.

And every block has its own pair. Block 7's W_up and block 8's W_up are the same shape — they must be, or the blocks could not stack — but they hold entirely different numbers, learned independently. A 32-block model therefore contains 32 separate W_up matrices and 32 separate W_down matrices, which is what makes 134 million × 32 a real count rather than one matrix used over and over. (Contrast that with a single block, where one W_up serves every token position: shared across tokens, never shared across blocks.)

That comes to roughly 4.3 billion weights in the feed-forward networks alone — about two thirds of a 7-billion-parameter model, with attention accounting for nearly all the rest. If you have wondered where "70 billion parameters" physically are, this is the answer for most of them.

(SwiGLU, the gated pattern from the previous section, is this same widen-then-narrow with three narrower matrices instead of two. GPT-family models use the two-matrix layout above.)

One last reason to care where the parameters sit: interpretability research suggests this structure is where much of the model's factual knowledge lives, with W_up behaving like a set of keys and W_down like the values those keys retrieve. Lesson 1 said there is no database inside the model. This is the machinery that plays that role instead.

Lesson in one breath

A layer is: multiply by a weight matrix, add a bias, apply a nonlinearity. Stacking these without the nonlinearity would collapse into a single linear map, so the activation function is what makes depth worth anything.
